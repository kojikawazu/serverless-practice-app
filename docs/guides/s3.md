## S3 とは

ファイル（**オブジェクト**）を、入れ物（**バケット**）に、名前（**キー**）を付けて置くサービス。容量を先に決めず、置いた分だけ課金される。サーバーのディスクと違い、Lambda のように実行環境が使い捨てのものからでも、同じ場所に読み書きできる。

## 仕組み

### バケット・オブジェクト・キー

| 用語 | 意味（公式「What is Amazon S3?」） |
|---|---|
| バケット | オブジェクトの入れ物。名前とリージョンを決めて作り、後から変えられない |
| オブジェクト | データ本体と、それを説明するメタデータ（`Content-Type` など） |
| キー | バケットの中でオブジェクトを一意に指す名前。`exports/2026-11-08/abc.json` のような文字列 |

**フォルダは実在しない。** 汎用バケットの中は平らで、`exports/2026-11-08/` のような「フォルダ」は、キーの先頭の文字列（**接頭辞**、prefix）にすぎない。権限・ライフサイクルなどは、この接頭辞で対象を絞れる。

**汎用バケットの名前は、既定では全アカウントで一意**でなければならない（同じパーティションの中で）。そのため、自分のアカウントの名前を付けるなどして衝突を避ける。公式は、自分のアカウントだけが作れる名前空間（account regional namespace）にバケットを作ることも勧めている（公式「Security best practices for Amazon S3」）。

### 整合性

**オブジェクトの書き込み・削除は、成功の応答を受けた直後から読める**（強い読み取り後の書き込み整合性。公式「Amazon S3 data consistency model」）。同じキーへの書き込みが重なったら、後のタイムスタンプのものが残る。複数のキーをまとめて原子的に更新する手段は無い。

一方、**バケットの設定（作成・削除・バージョニングの有効化など）は結果整合**で、反映までに少し時間がかかることがある（同じページ）。

### 守りの設定

新しい汎用バケットは、既定で次の状態で作られる（公式「What is Amazon S3?」「Security best practices for Amazon S3」）。

| 設定 | 既定 | 意味 |
|---|---|---|
| ブロックパブリックアクセス | 有効 | バケット・オブジェクトの公開を、ポリシーや ACL の書き方に関係なく止める |
| オブジェクト所有者（Object Ownership） | `BucketOwnerEnforced`（ACL を無効） | アクセスの制御を IAM とバケットポリシーに一本化する |
| 既定の暗号化 | SSE-S3 | 置いたオブジェクトは、S3 が管理する鍵で保存時に暗号化される |

既定に無いものとして、公式は**HTTPS 以外のリクエストをバケットポリシーで拒否する**ことを勧めている（`aws:SecureTransport` が `false` のときに `Deny`）。拒否の書き方と評価の順序は [IAM 解説](iam.md#評価の順序)を参照。

### ライフサイクル

**ライフサイクルの規則**で、作成から一定の日数が過ぎたオブジェクトを自動で消せる（`Expiration`）。規則は接頭辞などで対象を絞れ、規則を付けた時点で既にあるオブジェクトにも効く（公式「Expiring objects」）。

- 消えるのは**期限の後、非同期**。期限から実際に消えるまで遅れることがある。期限を過ぎた後の保存料は課金されない（同じページ）
- 期限ちょうどに消えていることを前提にした処理を書かない

## このプロジェクトで使う理由

データ連携 Lambda の書き出し先のうち、**実物を使うのは S3 だけ**で、BigQuery・Cuenote FC はスタブにしている（09「[外部サービスのスタブ](../09-architecture-specification.md#外部サービスのスタブ)」）。S3 は費用がほぼかからず、`local` でも LocalStack で動くため、書き出しが本当に起きたことを中身で確かめられる。

| 設定 | このプロジェクト | 正本 |
|---|---|---|
| バケット名 | `serverless-practice-app-<stage>-exports-<アカウント ID>`。全アカウントで一意にするため、アカウント ID を付ける | 10「[命名](../10-miscellaneous-specification.md#コーディング規約命名)」 |
| キー | `exports/<UTC の日付>/<実行名>.json`。同じ実行を再実行すると同じキーに上書きされる | 05「[連携ファイル](../05-data-specification.md#連携ファイルexportfile)」 |
| 保持 | 接頭辞 `exports/` を 7 日で消す（ライフサイクル） | 04「[保持期間](../04-non-functional-specification.md#保持期間)」 |
| 公開・ACL・暗号化 | ブロックパブリックアクセスをすべて有効・`BucketOwnerEnforced`・SSE-S3 | 06「[データ保護](../06-security-specification.md#データ保護)」 |
| HTTPS 以外 | バケットポリシーで拒否する | 同上 |
| 書く権限 | データ連携 Lambda のロールに、`exports/*` への `s3:PutObject` だけ | 06「[認可](../06-security-specification.md#認可権限制御)」 |
| 削除 | `force_destroy = true`。`stack.sh <stage> down` で、中身ごとバケットを消す | `s3.tf` のコメント・04「[運用性](../04-non-functional-specification.md#運用性)」 |

バケットは Terraform が作り、名前を SSM パラメータ（`bucket/name`）に書き出す。CDK はそれをデータ連携 Lambda の環境変数 `BUCKET_NAME` に渡す（[SSM Parameter Store 解説](ssm.md)）。

## 特徴と制約

### 既定と同じ値を、明示して書いている

公開ブロック・`BucketOwnerEnforced`・SSE-S3 は、今の S3 では新しいバケットの既定と同じ（上記「[守りの設定](#守りの設定)」）。`s3.tf` はそれでも 3 つとも明示している。値がコードに出るため、レビューで見え、既定が変わっても影響を受けない。既定と同じ値を明示する考え方は、Scheduler の `RetryPolicy` と同じ（[CDK 解説](cdk.md#既定値に頼るとテンプレートに値が出ない)）。

### 同じキーへの上書きと、前段の書き込みの残り

連携ファイルのキーは実行名で決まるため、同じ実行を再実行すると上書きになる（後勝ち）。別の実行は別のキーになり、重ならない。

データ連携は S3 → BigQuery → Cuenote FC の順に書き、途中で失敗しても前段の書き込みは消さない（元資料のリスク 4。03「[データ連携 Lambda](../03-functional-specification.md#データ連携-lambdadata-sync)」）。`failAt: "dataSync"` は S3 に書いた後に失敗するため、**実行は `FAILED` でも、S3 には連携ファイルが残る**。

### 作った直後のバケットは、存在の確認に 404 を返すことがある

バケットの作成は結果整合（上記「[整合性](#整合性)」）。Terraform の state を置くバケットを作るスクリプトで、作った直後の `head-bucket` が実 AWS で 404 を返し、スクリプトが自分のバケットの作り直しに進んで失敗した。LocalStack では起きなかった（教訓ログ「[作成直後の S3 バケットが head-bucket に 404 を返し、state バケットの作成スクリプトが自分のバケットの作り直しで失敗した](../lessons-learned.md#2026-10-11-作成直後の-s3-バケットが-head-bucket-に-404-を返しstate-バケットの作成スクリプトが自分のバケットの作り直しで失敗した)」）。データ連携の出力先バケットは Terraform が作るため、この問題には当たっていない。

### 料金

保存料とリクエスト料がかかる。このデモの連携ファイルは 1 実行あたり 1 つ（配信対象 3 件分の JSON）で、7 日で消える。09「[費用](../09-architecture-specification.md#費用)」は、S3 を含む従量課金を「デモの実行量なら無料枠に収まる見込み」としている。単価は本書では確かめていない。

## LocalStack との違い

| 違い | 正本 |
|---|---|
| 書き込み・読み出しは `local` でも動き、連携ファイルができたこと・失敗しても残ることを IT で確かめている | 08「[テストケース](../08-test-specification.md#テストケース)」の #20・#21・#35 |
| 既定で IAM を評価しないため、データ連携 Lambda の `s3:PutObject` の権限が足りなくても書ける。バケットポリシーの HTTPS 以外の拒否も、評価されていることを確かめていない | [IAM 解説](iam.md#localstack-との違い) |
| 作った直後のバケットの 404 は、LocalStack では起きなかった | 上記 |
| ライフサイクルで実際に消えるかは確かめていない（7 日待つ必要がある） | — |

## つまずきやすい点

| 症状 | 原因と対処 |
|---|---|
| バケットの作成が「名前が既に使われている」で失敗する | 汎用バケットの名前は全アカウントで一意。アカウント ID など、自分にしか無い文字列を付ける |
| 「フォルダ」を消したのに、中身のオブジェクトが残っている（または、その逆） | フォルダは実在せず、キーの接頭辞にすぎない。接頭辞で一覧して 1 つずつ消す |
| 作った直後のバケットに対して、存在の確認が 404 を返す | バケットの作成は結果整合。少し待って確かめ直す。404 を「無い」と決めつけて作り直さない |
| 7 日を過ぎたのに連携ファイルが残っている | ライフサイクルの削除は非同期で、期限から遅れることがある。期限後の保存料はかからない |
| `curl http://...` でバケットにアクセスすると拒否される | バケットポリシーが HTTPS 以外を拒否している。明示の拒否は許可より強い |
| `failAt: "dataSync"` で失敗させたのに、S3 に連携ファイルがある | 仕様どおり。S3 に書いた後で失敗させている。前段の書き込みは消さない |
