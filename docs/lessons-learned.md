## 2026-10-18 既定に頼っていた StateMachineType を明示しただけで、CloudFormation が置換とみなしてデプロイが失敗した

### 概要

#90 で、ステートマシンの種類を CDK に明示した（`stateMachineType: STANDARD`。既定も Standard で、実際の値は変わらない）。UT・型チェック・Lint は通ったが、デプロイ済みの `local` のスタックへの上書きが `StateMachineAlreadyExists` で失敗した。LocalStack ではロールバックの後もリソースが残り、作り直しも失敗したため、LocalStack ごと作り直した。

### 詳細

- 何が起きたか: `scripts/cdk.sh local deploy` で、CloudFormation が `StateMachineType` の追加を置換として扱い、同じ名前のステートマシンを先に作ろうとして失敗した。スタックは `UPDATE_ROLLBACK_COMPLETE` になったが、ステートマシンは一覧から消え、`stack.sh local down` → `up` ではロググループが「既にある」で失敗した。影響は `local` だけで、`dev` には適用していない
- なぜ起きたか（根本原因）: 「実際の値は変わらないので無害」と判断し、CloudFormation が項目の有無の差分で更新の方法を決めることを確かめなかった。`StateMachineType` の更新は Replacement で、名前を指定したリソースは置換できない（公式のリファレンス）。このデモは関数・ステートマシンの名前を命名規約で固定しているため、置換を伴う変更はどれも上書きできない。CDK の UT は合成したテンプレートの形を見るだけで、既存のスタックからの更新で何が起きるかは見ない
- 教訓 / 次からどうする: CDK のテンプレートを変えたら、デプロイの前に `cdk diff`（`local` なら `npx cdklocal diff -c stage=local`）を実行し、`replace` の印が無いかを見る。印があり名前を固定しているなら、上書きはできないので、PR に移行手順（`stack.sh <stage> down` → `up`）を書く。UT が通ることを、デプロイが通ることの根拠にしない
- 関連: #90、09「Step Functions の流れ」、[CDK 解説](guides/cdk.md#明示しただけで作り直しになることがある)

## 2026-10-18 ハートビート切れのエラー名を、観測しないまま States.HeartbeatTimeout と仕様に書いていた

### 概要

03・07・09 は、`DataSync` のハートビートが切れたときのエラー名を `States.HeartbeatTimeout` としていた。#90 で LocalStack で観測すると `States.Timeout` だった。2026-10-13 の「TIMED_OUT の実行の error を、観測しないまま States.Timeout と仕様に書いていた」と同じ種類の誤りで、しかも同じ日に書いていた。

### 詳細

- 何が起きたか: 2026-10-13 の LMI の設計（58a31b5）で、公式のエラー処理のページにある `States.HeartbeatTimeout` を、ハートビート切れの名前として書いた。#79（Step Functions の解説）の調べで、公式の Task ステートのページは `States.Timeout` と書いていて記述が揺れていると分かった。`Retry` の対象にはどちらの名前も入っていないため、挙動への影響は無い。ずれていたのは、通知に出るエラー名と仕様書の記述
- なぜ起きたか（根本原因）: エラー名を、公式の 1 ページの定義から書き、実行を観測しなかった。名前は通知・実行の結果・実行履歴に出る値で、どこに何が出るかは動かすまで分からない。同じ日に TIMED_OUT のエントリで「観測してから書く」と決めたが、その日に書いた他のエラー名（LMI の設計の分）を見直していなかった
- 教訓 / 次からどうする: 外部サービスが出す値（エラー名・項目の有無・ID の形）を仕様に書くときは、観測した API と項目まで添える。観測していない値は「未観測」と書き、出どころ（公式のどのページか）を添える。同じ種類の誤りを 1 つ直したら、同じ方法で書いた他の値も洗い出して観測する
- 関連: #90、#79、本ログの 2026-10-13「TIMED_OUT の実行の error を、観測しないまま States.Timeout と仕様に書いていた」・2026-10-17「試していない構成の結果を、確かめた事実と同じ書き方で 09 に書きかけた」（同じ種類の誤り）、09「LocalStack での検証結果」。**同じ種類の誤りが繰り返されているため、ルール（`.claude/rules/`）への昇格の候補**

## 2026-10-17 予算アラートの額を最悪の費用で決め、最も安い消し忘れでは越えない額にしていた

### 概要

#65 で、LMI の消し忘れに備える予算アラートを日次 3 USD にした。根拠は「3 台のまま消し忘れると約 $8/日」だった。実際は約 8 分後に 1 台に減り、許可したタイプのうち安い `m6g.large` が選ばれると約 $2.85/日で、3 USD を一度も越えない。#72 で 1 USD に下げた。

### 詳細

- 何が起きたか: `dev` の予算（アカウント単位・日次 3 USD）は、`m6g.large` 1 台の消し忘れを通知できない設定のまま、2026-10-15 から 10-17 まで置かれていた。この間に消し忘れは無く、実害は無い。#66 の検証で 1 台に減ることが分かり（`m7g.large` で約 $3.03/日）、#72 で単価を Pricing API で引き直して、`m6g.large` では越えないことが分かった
- なぜ起きたか（根本原因）: 額を「費用の見積もり」と同じ考え方で決めた。見積もりは費用の上限を知るためのもので、高い方（3 台・高いタイプ）で計算するのが正しい。アラートは消し忘れを確実に捕まえるためのもので、確かめるべきは最も安く済む消し忘れ（台数が減った後・安いタイプ）でも越えるかだった。09 にも「見積もりは候補のうち高い方で行う」とあり、その考え方を額の決定にもそのまま使った
- 教訓 / 次からどうする: 閾値で異常を検知するもの（予算・アラーム）の額を決めるときは、「越えなければならない最小のケース」と「越えてはならない最大のケース」を表で並べ、閾値がその間にあることを数値で示す。前者には、自動で縮む構成（実行環境の最小値まで減る）や、複数の候補（インスタンスタイプ）のうち安い方を使う。後者は、推測ではなく Cost Explorer などの実績で確かめる
- 関連: #72、#65、#66、09「予算アラート」の「額の決め方」

## 2026-10-17 試していない構成の結果を、確かめた事実と同じ書き方で 09 に書きかけた

### 概要

#71 で、`depends_on` を付けない構成では「ロググループが作り直されていた」と 09・`lmi.tf` のコメントに断定で書いた。その構成は dev で試しておらず、推論だった。コミット前のセルフレビューで「作り直されうる（試していない）」に直した。同じ日の #70 のエントリ（推論を観測で確かめずに結論にした）と同じ種類の誤りの繰り返し。

### 詳細

- 何が起きたか: #71 の `down` で、最後のインスタンスがプロバイダの削除の後に終わったことを CloudTrail で確かめた。そこから「並行して消していれば、この終了のログで作り直されていた」と書いた。確かめたのは「付けた構成で作り直されない」ことだけで、「付けない構成で作り直される」ことは試していなかった。同じ段落で、プロバイダの削除の時刻を「関数の削除の 2 分後」（実際は 91 秒後）とも書いていた
- なぜ起きたか（根本原因）: 観測した事実（削除の順序・LMI が無ければ作ること）と推論（だから作り直される）を、同じ段落で同じ文体（断定）で書いた。直前の観測が設計の懸念を裏付けたため、残りも確かめたつもりになった。数値も、時刻の表から計算せずに印象で書いた
- 教訓 / 次からどうする: 検証結果を書くときは、1 文ごとに「確かめた / 確かめていない」を分け、確かめていないものには「〜しうる」「試していない」と書いて根拠（何から推論したか）を添える。時刻の差などの数値は、書く前に元の記録から計算し直す。セルフレビューでは、検証結果の節の断定文を 1 つずつ、どの観測が根拠かを突き合わせる
- 関連: #71、#70、本ログの 2026-10-17「LMI の非同期の再試行設定を『付いている版』から推論し、効いていないと誤認した」（同じ種類の誤り）、09「`dev` での検証結果」の「LMI」

## 2026-10-17 terraform graph -type=plan-destroy が state の無い環境で空のグラフを返し、順序の検査が空振りしかけた

### 概要

#71 で `depends_on` による削除の順序を手元で確かめようと、`terraform graph -type=plan-destroy` を実行した。このグラフは state にあるリソースから作るため、state の無い手元のコピーでは `root` しか無い空のグラフになった。「プロバイダのノードが 0 件なら失敗」の検査を入れていたので気づけたが、無ければ「辺が無い＝順序が付いていない」と誤読していた。

### 詳細

- 何が起きたか: dev の backend 設定を持つ作業ディレクトリに触れないよう、`.tf` をスクラッチに複製し、backend を local に差し替えて `graph -type=plan-destroy` を実行した。出力は 6 行で、リソースのノードが 1 つも無かった。`-type` を付けない `terraform graph`（設定から依存を要約する。state を見ない）に切り替えると 88 行になり、「プロバイダ → ロググループ」の辺が見えた。`depends_on` から外すと辺が消えることも確かめた
- なぜ起きたか（根本原因）: `-type=plan-destroy` は「この state を消すときの操作のグラフ」であり、消すものが無ければ操作も無い。設定の依存を見たいのに、state に依存する種類のグラフを選んでいた。出力が空でも終了コードは 0 で、エラーにはならない
- 教訓 / 次からどうする: 設定の依存（`depends_on`・参照）を確かめるときは `-type` を付けない `terraform graph` を使う。Terraform は依存の逆順で消すため、依存の辺があれば削除の順序も決まる。グラフから辺を探す検査では、先に対象のノードが 1 つ以上あることを確かめ、0 件なら失敗にする（`quality-gate.md`「『対象が 0 件』と『検査して 0 件』を区別する」）
- 関連: #71、09「`dev` での検証結果」の「LMI」、`.claude/rules/quality-gate.md`

## 2026-10-17 LMI の非同期の再試行設定を「付いている版」から推論し、効いていないと誤認した

### 概要

#66 で、データ連携 Lambda の再試行 0 は `$LATEST` にしか付いておらず、実行は `$LATEST.PUBLISHED` で動くことから、「効いていないかもしれない」と判断した。#70 で `$LATEST.PUBLISHED` にも設定を付けて dev で確かめたところ、修飾子なしの呼び出しには元から `$LATEST` の設定が効いており、足した設定はステートマシンからの呼び出しに効かなかった。

### 詳細

- 何が起きたか: #70 で `$LATEST.PUBLISHED` に `EventInvokeConfig`（再試行 0）を足す実装と UT を書き、dev で関数エラーを起こすと起動は 1 回だった。ここで「付けたから効いた」と結論しかけたが、対照として `$LATEST.PUBLISHED` だけ再試行 2 にしても 1 回だった。`$LATEST` だけ再試行 2 にすると 3 回、`:$LATEST.PUBLISHED` を付けて呼ぶと `$LATEST.PUBLISHED` の設定で 3 回になった。実装と UT は戻し、コメントと 09 を確かめた事実に直した
- なぜ起きたか（根本原因）: 「設定がどの版に付いているか」と「実行がどの版で動くか」の 2 つの観測から、「どの設定が効くか」を推論した。非同期の呼び出しの設定は、実行される版ではなく**呼び出し側が指定した修飾子**で決まる。推論の材料はどちらも正しかったが、2 つを結ぶ規則が推測だった。また、効いているときの観測（起動 1 回）は「設定が効いた」と「観測の方法が再試行を拾えない」を区別できず、それだけでは推論の誤りが見えなかった
- 教訓 / 次からどうする: 「設定がどこにあるか」を「その設定が効くか」の根拠にしない。効くかどうかは、**その設定の値を変えて結果が変わること**（対照）で確かめる。期待どおりの結果が「何も起きない」形のとき（再試行 0 → 1 回）は特に、起きる側の値（再試行 2 → 3 回）でも同じ手順を通し、観測が空振りしていないことを先に示す（`quality-gate.md`「検査は壊して確かめる」）
- 関連: #70、#66、09「`dev` での検証結果」の「LMI」、2026-10-17 の LMI のインスタンスが見えなかったエントリ（同じ検証で、0 件を「無い」と読みかけた誤り）

## 2026-10-17 偽の AWS が実物の省略する項目を常に返し、予算スクリプトの冪等性の欠陥を UT で見逃した

### 概要

`scripts/budget-alert.sh` は、実 AWS が既定値の `ThresholdType: PERCENTAGE` を通知の応答から省くため、作った直後の予算を「ずれ 2 件」と判定し、実行のたびに通知を消して作り直していた。UT は、偽の AWS（`test/scripts/helpers/fake-aws.ts`）が `ThresholdType` を常に返していたため通っていた。

### 詳細

- 何が起きたか: 2026-10-15、#66 の準備で `dev` に初めて予算を作った直後の `--check` が 1 で終わった。予算と通知そのものは正しく作られていた。`--check` なしで実行すると、同じ通知を「余分」として消し「不足」として作り直す。UT（08 #43〜#46）はすべて通っていた
- なぜ起きたか（根本原因）: 偽の AWS の応答を、スクリプトが**渡した値をそのまま返す**形で作った。額の小数化・`NotificationState`・予算の補完項目は「実 AWS に寄せる」として意識的に再現したが、それは既知の差分だけで、未知の差分（既定値の項目の省略）は再現しようがなかった。偽物を作った時点で実物の応答を一度も観測しておらず、偽物は「実物はこう返すはず」という推測だった。冪等性の検査（2 回目は変更なし）は、偽物が往復で値を保つ限り必ず通るため、この種の欠陥を構造的に検出できない
- 教訓 / 次からどうする: 外部 API の偽物は、**実物の応答を一度観測してから**、その形で返すように作る（観測できない段階で作るなら、偽物の冒頭に「推測で作った」と書き、実物で初めて動かしたときに応答を偽物と突き合わせる）。比較で「そろっている」と判定するスクリプトは、作成の直後に実物で `--check` を 1 回動かすところまでを作業の完了条件に入れる。偽物を実物に合わせたら、修正の前にテストが落ちることを確かめる（今回は 8 件が落ちた）
- 関連: #69、#65、2026-10-13 のエントリ（外部サービスが作る値を観測せずに仕様に書いた。同じ型の誤りが、今回はテストの偽物の側で起きた）、09「予算アラート」、08 #44

## 2026-10-17 LMI のインスタンスが describe-instances の既定の応答に出ず、動いているのに 0 台に見えた

### 概要

#66 で LMI をデプロイした直後、`aws ec2 describe-instances` が 0 件を返した。実際には 3 台が動いており、`--include-managed-resources` を付けたときだけ出た。削除後の「インスタンスが 0 件」の確認をこのコマンドで行っていたら、消し忘れていても確認済みになっていた。

### 詳細

- 何が起きたか: デプロイ後に状態フィルタ付きの `describe-instances` を実行すると `[]` だった。キャパシティプロバイダのログには起動の記録があり、食い違いから調べると、LMI のインスタンスには `Operator`（`Managed: true`・`Principal: scaler.lambda.amazonaws.com`・`HiddenByDefault: true`）が付いており、既定の応答から隠されていた。09 の手順（削除後に 0 件を確かめる）は、このコマンドでも書けてしまう形だった
- なぜ起きたか（根本原因）: AWS のサービスが利用者のアカウントに作るリソース（managed resources）は、既定で一覧の API から隠されることがある。「アカウント内の EC2 は `describe-instances` に全部出る」という前提で数えていた。0 件は「無い」と「見えていない」を区別できず、ログという別の情報源が無ければ気づけなかった
- 教訓 / 次からどうする: AWS のサービスが代わりに作るリソース（LMI の EC2 など）を数えるときは、まず管理対象を含める指定（`--include-managed-resources`）を付ける。削除後の 0 件の確認では、同じ条件で終了済みを含む全状態も出し、**消したはずのリソースが `terminated` として見えること**で、検査が空振りしていないことを確かめる（`quality-gate.md` の「対象が 0 件」と「検査して 0 件」の区別）
- 関連: #66、09「`dev` での検証結果」の「LMI」、08 #36、`.claude/rules/quality-gate.md`

## 2026-10-13 TIMED_OUT の実行の error を、観測しないまま States.Timeout と仕様に書いていた

### 概要

07「エラー」は仕様書の作成時から、`TIMED_OUT` の実行の `error` を `States.Timeout` としていた。実 AWS で観測すると、実行には `error` / `cause` の項目そのものが無く、`States.Timeout` は実行履歴のイベントにだけ出た。通知 Lambda が値の欠落を `null` に揃える作りだったため、実害は出なかった。

### 詳細

- 何が起きたか: 仕様書の作成時（2026-10-08）に、`States.Timeout` を「ステートマシンが 5 分を超えたときの実行結果のエラー名」として表に載せた。#46 の IT で LocalStack の値が `null` と分かり「実 AWS は未観測」と注記したが、実 AWS の値は #44（2026-10-13）まで確かめていなかった。観測では、`describe-execution` の結果に `error` / `cause` が無く、`States.Timeout` は最後のイベント `ExecutionTimedOut` の `error` にだけ出た。通知に届く値も `null` だった
- なぜ起きたか（根本原因）: AWS が作る値（自分のコードが出す値ではない）を、名前の知識から「実行結果に入る」と推測して書いた。`States.Timeout` という名前自体は実在するが、**どこに出るか**（実行の結果か、実行履歴か、状態変化イベントか）は値ごとに違い、名前を知っていることは置き場所を知っていることにならない。仕様の表は「エラー名 → 実行結果」の形だったため、置き場所の違いを書く欄が無かった
- 教訓 / 次からどうする: 外部サービスが作る値を仕様に書くときは、**観測した値か推測かを書き分け、推測なら「未観測」と書いてから観測する issue を立てる**。観測するときは、名前だけでなく「どの API の、どの項目に出るか」まで記録する。受け取る側（今回の通知 Lambda）は、観測前の値を当てにせず、`null` と項目の欠落の両方を受け付けて揃えておく（03「Slack 通知 Lambda」の作りが、今回の推測の誤りを吸収した）
- 関連: #44、#46、#57（IT で `error` / `cause` を確かめる）、07「エラー」、09「`dev` での検証結果」

## 2026-10-12 壊す検証で前提を作るスクリプトが失敗し、何も壊れていないまま「通った」を観測した

### 概要

#46 で「途中で止まった IT が書き換えた定義を、次の IT が戻すか」を確かめるため、書き換えたまま残った状態をスクリプトで作ってから IT を流した。スクリプトは失敗していたが同じ一連のコマンドの中で処理が続き、何も書き換わっていない状態で IT が通った。終了コードを見て気づき、やり直した。

### 詳細

- 何が起きたか: 前提を作るスクリプト（`tsx` で実行する `.ts`）がトップレベルの `await` を CJS として変換できず、`shorten_rc=1` で終わった。続く「復元を外した IT」は、壊れているはずの状態が無いため通った。後ろのコマンドが成功していたため、結果だけを見ると「復元が無くても通る（復元は要らない）」という逆の結論を読みかねなかった
- なぜ起きたか（根本原因）: 前提の作成・検査・後始末を 1 つのコマンド列にまとめ、前提の作成が成功したかで検査に進むかを分けていなかった。さらに、前提が実際に成り立っているかを、検査の前に状態で確かめていなかった。スクリプトはリポジトリの外（スクラッチ領域）に置いたため、`package.json` の `"type": "module"` が効かず CJS として扱われた
- 教訓 / 次からどうする: 壊す検証では、前提を崩す操作と検査の間に**崩れた状態をコマンドで確かめる手順**を挟み（今回は「定義に `ItTimeoutWait` があり、タイムアウトが 2 秒」を出力した）、成り立っていなければ検査に進まない。前提を作るコマンドの終了コードは、検査の結果より先に読む。リポジトリの外で TypeScript を `tsx` で動かすときは、ESM を明示する拡張子（`.mts`）にする
- 関連: #46、`.claude/rules/quality-gate.md`（検査は壊して確かめる・「対象が 0 件」と「検査して 0 件」を区別する）

## 2026-10-12 Dependabot 自身が PR で設定を検証していることを確かめず、同じ観点の検査を足しかけた

### 概要

「`dependabot.yml` の誤りは GitHub がマージ後に Insights に出すだけで、CI は緑のまま」と思い込み、独自のスキーマ検証（`check-jsonschema`）を CI に足す PR を作った。実際には、Dependabot 自身が `dependabot.yml` を変更する PR に検証のチェックを付けており、同じ観点の二重化になるため PR を閉じた。

### 詳細

- 何が起きたか: #37 の残課題に上記の前提を書き、#38 で起票、#39 で検査を実装した。#39 で設定をわざと壊したコミットを積むと、独自の検査と並んで GitHub 側の `.github/dependabot.yml` チェック（app: dependabot）も失敗した。このチェックは、`dependabot.yml` を新規に追加した #37 には付いておらず、main に設定が入った後の #39 で初めて付いた
- なぜ起きたか（根本原因）: 「誤りが検出されない」という前提は、ドキュメントの記述（Insights に表示される）からの推測で、どの PR でも確かめていなかった。仮に #37 のチェック一覧を見ていても、新規追加の PR にはチェックが付かないため、同じ誤った結論になっていた。設定が main に入った後の状態で、壊した設定を PR に出して確かめる必要があった。検査の要否を「既存の仕組みが何を見ているか」ではなく「自分の手元の検査が何を見ているか」で判断した
- 教訓 / 次からどうする: 「〇〇の誤りは検出されない」を理由に検査を足す前に、**検査を足す前の状態で**わざと壊したものを PR に出し、既存のチェック（GitHub やアプリが付けるものを含む）が落ちないことを確かめる。PR のチェック一覧に自分が足していないものがあれば、名前と app を見て何を検査しているかを把握する。既存のチェックは「初回の追加」と「追加後の変更」で付き方が変わり得るため、確かめるのは後者の状態で行う。「壊して確かめる」は新しい検査の効きを確かめるだけでなく、検査が要るかどうかの判断にも先に使う
- 関連: #37、#38、#39、#40、`.claude/rules/quality-gate.md`（検査は壊して確かめる）、`.claude/rules/static-analysis.md`（自前の検査と役割が重なる場合は担当を 1 つに決める）

## 2026-10-11 バッチ起動スクリプトが、認証切れを「ステートマシンが無い（デプロイ漏れ）」と案内していた

### 概要

`scripts/batch.sh` の ARN を引く関数が `aws` の失敗を見ておらず、`aws login` のセッション切れで、デプロイ済みなのに「見つかりません。デプロイしてください」と表示した。止まりはしたが、原因と逆の対処へ誘導していた。

### 詳細

- 何が起きたか: #23 で `dev` の実行を起動しようとした際、セッション切れで `list-state-machines` が失敗したのに、デプロイ漏れのメッセージが出た。`local` では認証が要らないため、`dev` で初めて表面化した
- なぜ起きたか（根本原因）: 関数が `arn="$(state_machine_arn)"` とコマンド置換の中で呼ばれており、bash 3.2（macOS 標準。`inherit_errexit` が無い）ではそこに `set -e` が引き継がれない。そのため関数内の `aws` が失敗しても処理が続き、空の出力を「該当なし」の分岐で受けた。「取得できなかった」と「無かった」を同じ値（空文字）で表していた
- 教訓 / 次からどうする: コマンド置換の中で呼ばれる関数では、外部コマンドの失敗を `if ! x="$(cmd)"; then ... fi` で明示的に判定し、「取得の失敗」と「結果が空」を別の分岐・別のメッセージにする。`set -e` に頼れるのはトップレベルの代入だけと考える。同じ日に `scripts/terraform.sh` でも `eval "$(cmd)"` が変換の失敗を握り潰す形を同じ書き方で避けており、シェルで繰り返し現れる型である
- 関連: #23、`.claude/rules/error-handling.md`（判定不能を正常値に丸めない）、`scripts/batch.sh`、`scripts/terraform.sh`

## 2026-10-11 Terraform 1.14 が aws login のプロファイルを読めず、dev へ plan できなかった

### 概要

MFA 付き IAM ユーザーで `aws login --profile` した認証を、AWS CLI と CDK は読めるが Terraform 1.14.3 は読めず、`No valid credential sources found` で止まった。`scripts/terraform.sh` で一時的な認証情報へ変換して渡すようにした。

### 詳細

- 何が起きたか: #23 で `scripts/terraform.sh dev init/plan` を実行すると、同じ `AWS_PROFILE` で AWS CLI は通るのに Terraform だけ認証に失敗した。長期のアクセスキーを発行しない方針のため、アクセスキーで回避する選択肢も無かった
- なぜ起きたか（根本原因）: `aws login` が書くプロファイルには `login_session` しか無く、アクセスキーも `credential_process` も含まない（認証情報は `~/.aws/login/cache` に置かれる）。Terraform 1.14.3（AWS プロバイダ 6.68.0）はこの形のプロファイルから認証情報を得られなかった。ツールごとに SDK とそのバージョンが違うため、「CLI で通る」ことは「他のツールでも通る」根拠にならない
- 教訓 / 次からどうする: 新しい認証方式を採るときは、使う全ツール（AWS CLI・CDK・Terraform）でそれぞれ `sts get-caller-identity` 相当が通るかを最初に確かめる。読めないツールには `aws configure export-credentials --format env` で一時的な認証情報へ変換し、ファイルに書かず環境変数でそのプロセスにだけ渡す。変換の失敗が握り潰されないよう、代入と `eval` を分けて終了コードを見る
- 関連: #23、docs/09「ステージ」、`scripts/terraform.sh`

## 2026-10-11 作成直後の S3 バケットが head-bucket に 404 を返し、state バケットの作成スクリプトが自分のバケットの作り直しで失敗した

### 概要

`scripts/tfstate-bucket.sh dev` は、`head-bucket` の 404 を「バケットが無い」と判定して作成する。実 AWS では、作ったばかりの自分のバケットに `head-bucket` が 404 を返し、作成に進んで `BucketAlreadyOwnedByYou` で止まった。LocalStack の IT では起きなかった。

### 詳細

- 何が起きたか: #23 で state バケットを実 AWS に作る際、作ったばかりの自分のバケットについて `head-bucket` が 404 を返し、スクリプトが作成に進んで `BucketAlreadyOwnedByYou` で失敗した
- なぜ起きたか（根本原因）: スクリプトが「`head-bucket` が 404 なら無い」という前提で作成に進んでいた。実 AWS ではこの前提が作成直後に崩れることがあり、LocalStack では崩れないため IT で見つからなかった。作成直後に 404 が返る AWS 側の仕組みまでは確かめていない

- 関連: #23、#19（PR #35）、docs/09「Terraform の state」、`scripts/tfstate-bucket.sh`

## 2026-10-09 失敗通知 Lambda が、通知に使わない日時項目の形の違いで失敗通知を捨てていた

### 概要

Slack 通知 Lambda の入力スキーマが、通知に使わない `startDate` / `stopDate` まで数値として検証していた。LocalStack はこれを文字列で届けるため、ステートマシンが `FAILED` になっても「通知対象外」として警告ログだけを出し、失敗通知が一件も出なかった。

### 詳細

- 何が起きたか: #20 で CDK スタックを LocalStack にデプロイし `{"failAt":"dataSync"}` で実行したところ、実行は `FAILED` になったが Slack スタブへの出力が無かった。`local` ステージでは失敗通知が全く機能せず、docs/02 の受け入れ条件を満たせない状態だった。本物の AWS では数値で届くため、`dev` だけで確かめていれば見逃していた
- なぜ起きたか（根本原因）: スキーマを「AWS ドキュメント上のイベントの形」から書き起こし、ハンドラが実際に使う項目に絞らなかった。通知 Lambda は「検証に落ちたイベントは対象外として正常終了する」設計で（再試行しても結果が変わらないため）、そのため使わない項目の形の違いが、エラーではなく「通知しない」という正常に見える結果になった。さらに UT に「`startDate` が文字列なら拒否する」ケースがあり、fail-unsafe な挙動を仕様として固定していた

- 関連: #30、#20、`.claude/rules/error-handling.md`（判定不能を正常値に丸めない）、docs/07「状態変化イベント」

## 2026-10-08 JSDoc 必須ルールが JSDoc を付けた export const まで欠落と報告していた

### 概要

`jsdoc/require-jsdoc` のセレクタ `ExportNamedDeclaration > VariableDeclaration` が、JSDoc の有無に関係なくすべての `export const` を報告していた。回帰テストを入れていたのに、fixture が「JSDoc 無しの export const」しか持たず、誤りを検出できなかった。

### 詳細

- 何が起きたか: M2（#8）で入れた ESLint 設定のまま、M3（#10）で JSDoc を付けたスキーマ定数 8 件を書いたところ、すべて「Missing JSDoc comment」で Lint が落ちた。M2 の時点では `functions/src` が空で、実コードに当たって初めて顕在化した
- なぜ起きたか（根本原因）: JSDoc は `export` 文（`ExportNamedDeclaration`）の前に付くが、セレクタは子の `VariableDeclaration` を対象にしていたため、ルールから JSDoc が見えなかった。関数・クラス・型のセレクタは子を指しても JSDoc を見つけられるため、定数だけが壊れていた。回帰テストの fixture は「検出されるべきもの / されてはならないもの」を全体では両方持っていたが、定数については「されるべきもの」しか無く、常に報告するセレクタと正しいセレクタを区別できなかった
- 教訓 / 次からどうする: 検出ルールの fixture は、対象の構文ごとに「検出されるケース」と「検出されないケース」を 1 つずつ置く。全体で両方そろっているだけでは足りない。設定例を規約から写すときも、写した構文ごとに陰性ケース（ここでは JSDoc 付き）を fixture に足してから採用する
- 関連: `.claude/rules/jsdoc.md`（「対象は AST セレクタで指定する」「検出結果を回帰テストに固定する」を本件で改訂）、#10、#11
