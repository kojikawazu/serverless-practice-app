## 2026-10-09 失敗通知 Lambda が、通知に使わない日時項目の形の違いで失敗通知を捨てていた

### 概要

Slack 通知 Lambda の入力スキーマが、通知に使わない `startDate` / `stopDate` まで数値として検証していた。LocalStack はこれを文字列で届けるため、ステートマシンが `FAILED` になっても「通知対象外」として警告ログだけを出し、失敗通知が一件も出なかった。

### 詳細

- 何が起きたか: #20 で CDK スタックを LocalStack にデプロイし `{"failAt":"dataSync"}` で実行したところ、実行は `FAILED` になったが Slack スタブへの出力が無かった。`local` ステージでは失敗通知が全く機能せず、docs/02 の受け入れ条件を満たせない状態だった。本物の AWS では数値で届くため、`dev` だけで確かめていれば見逃していた
- なぜ起きたか（根本原因）: スキーマを「AWS ドキュメント上のイベントの形」から書き起こし、ハンドラが実際に使う項目に絞らなかった。通知 Lambda は「検証に落ちたイベントは対象外として正常終了する」設計で（再試行しても結果が変わらないため）、そのため使わない項目の形の違いが、エラーではなく「通知しない」という正常に見える結果になった。さらに UT に「`startDate` が文字列なら拒否する」ケースがあり、fail-unsafe な挙動を仕様として固定していた
- 教訓 / 次からどうする: 外部イベントの入力スキーマは、ハンドラが読む項目だけを検証する（Zod の `z.object` は未知キーを取り除くので、型の安全性は落ちない）。特に「検証失敗 = 処理しない」で正常終了するハンドラでは、検証項目を 1 つ足すたびに「この項目の形が違ったら、本来の処理を捨ててよいか」を問う。異常系のテストを書くときも、拒否するケースが「捨ててよい入力」かどうかを確かめてから固定する。ステートマシン・ルール側で絞り込んでいる値（`stateMachineArn` 等）は、ハンドラ側で重ねて検証しない
- 関連: #30、#20、`.claude/rules/error-handling.md`（判定不能を正常値に丸めない）、docs/07「状態変化イベント」

## 2026-10-08 JSDoc 必須ルールが JSDoc を付けた export const まで欠落と報告していた

### 概要

`jsdoc/require-jsdoc` のセレクタ `ExportNamedDeclaration > VariableDeclaration` が、JSDoc の有無に関係なくすべての `export const` を報告していた。回帰テストを入れていたのに、fixture が「JSDoc 無しの export const」しか持たず、誤りを検出できなかった。

### 詳細

- 何が起きたか: M2（#8）で入れた ESLint 設定のまま、M3（#10）で JSDoc を付けたスキーマ定数 8 件を書いたところ、すべて「Missing JSDoc comment」で Lint が落ちた。M2 の時点では `functions/src` が空で、実コードに当たって初めて顕在化した
- なぜ起きたか（根本原因）: JSDoc は `export` 文（`ExportNamedDeclaration`）の前に付くが、セレクタは子の `VariableDeclaration` を対象にしていたため、ルールから JSDoc が見えなかった。関数・クラス・型のセレクタは子を指しても JSDoc を見つけられるため、定数だけが壊れていた。回帰テストの fixture は「検出されるべきもの / されてはならないもの」を全体では両方持っていたが、定数については「されるべきもの」しか無く、常に報告するセレクタと正しいセレクタを区別できなかった
- 教訓 / 次からどうする: 検出ルールの fixture は、対象の構文ごとに「検出されるケース」と「検出されないケース」を 1 つずつ置く。全体で両方そろっているだけでは足りない。設定例を規約から写すときも、写した構文ごとに陰性ケース（ここでは JSDoc 付き）を fixture に足してから採用する
- 関連: `.claude/rules/jsdoc.md`（「対象は AST セレクタで指定する」「検出結果を回帰テストに固定する」を本件で改訂）、#10、#11
