## パフォーマンス要件

処理量はデモ用の固定データ（配信対象 3 件）で、性能目標は置かない。代わりに、失敗の結果が待てる時間で見えることを要件にする。

| 対象 | 値 | 根拠 |
|---|---|---|
| 投入 Lambda のタイムアウト | 30 秒 | `SendMessageBatch` 数回で終わる。Retry を含めてもステートマシンのタイムアウトに収まる |
| Consumer Lambda のタイムアウト | 10 秒 | スタブへの出力のみ。DLQ 到達までの時間を短くするため小さく取る |
| データ連携 Lambda のタイムアウト | 1,800 秒（`local` は 900 秒） | 検証用の待ち（`holdSeconds` の上限 1,200 秒）に処理の余裕を足す。15 分を超えられるのは LMI で非同期に呼ぶ `dev` だけで、`local` は通常の Lambda の上限（09「LMI（Lambda Managed Instances）」） |
| `DataSync` タスクのタイムアウト | 関数のタイムアウト + 60 秒（`dev` 1,860 秒・`local` 960 秒） | LMI はタイムアウトしてもコードを止めないため、ステートマシン側で必ず打ち切る |
| `DataSync` タスクのハートビートのタイムアウト | 300 秒 | 関数は待つ間 60 秒ごとに送る。結果を返せずに止まった関数を、タスクのタイムアウトより早く見切る |
| Slack 通知 Lambda のタイムアウト | 10 秒 | スタブへの出力のみ |
| Lambda のメモリ | 256 MB（データ連携 Lambda 以外） | 最小構成で足りる。cold start の短縮を兼ねる |
| データ連携 Lambda のメモリ | 2,048 MB | LMI の最小構成（vCPU あたり 2 GiB、1 vCPU）。`local` も同じ値にそろえる |
| ステートマシンのタイムアウト | 40 分 | 投入（Retry を含む）と `DataSync` のタイムアウトの合計より長くする。超えたら `TIMED_OUT` で通知に乗せる |
| SQS の可視性タイムアウト | 60 秒 | Consumer のタイムアウトの 6 倍（AWS 推奨） |
| DLQ 到達までの目安 | 約 3 分 | 可視性タイムアウト 60 秒 × 受信 3 回 |
| Consumer のバッチサイズ | 5 件 | 部分バッチ応答で 1 件ずつ成否を返す |

**連動するパラメータ**: SQS の可視性タイムアウトは Consumer のタイムアウトの 6 倍に保つ。片方だけ変えると、処理中のメッセージが再配信されて二重に処理される。ずれを検査で見つけるのではなく、ずれない構造にする: Consumer のタイムアウトの正本を Terraform の変数 `consumer_timeout_seconds` に置き、可視性タイムアウトはそこから 6 倍で計算する。CDK は同じ値を SSM（`consumer/timeout-seconds`）から読み、自分では値を持たない（05「SSM パラメータ」）。

## 可用性・信頼性

デモのため稼働率の目標は置かない。データは使い捨てで、バックアップは取らない。

### リトライ

| 対象 | 方式 | 対象のエラー | 回数・間隔 |
|---|---|---|---|
| EventBridge Scheduler → ステートマシン | Scheduler の再試行 | `StartExecution` の呼び出しの失敗 | 最大 185 回・24 時間（`RetryPolicy`。サービスの既定と同じ値を CDK で明示）。やり直しを使い切った呼び出しは DLQ（SQS 標準キュー）へ送り、アラームで通知する（下記「起動の失敗の通知」） |
| Step Functions の Lambda タスク | `Retry` | `Lambda.ServiceException` / `Lambda.AWSLambdaException` / `Lambda.SdkClientException` / `Lambda.TooManyRequestsException`。投入タスクのみ `EnqueuePartialFailureError` も対象 | 最大 2 回、初回 2 秒、倍率 2 |
| Consumer | SQS の再配信 | 失敗したメッセージすべて | 受信 3 回で DLQ（`maxReceiveCount: 3`） |
| Slack 通知 Lambda | 非同期呼び出しの再試行 | 関数のエラー | Lambda 既定（最大 2 回） |
| データ連携 Lambda | 非同期呼び出しの再試行 | — | **0 回**。同じタスクトークンで処理が二重に走らないようにする。やり直しは `DataSync` タスクの `Retry`（上の行）に任せる。関数が `SendTaskFailure` で返したエラー名にも同じ `Retry` が効く |

注入エラー（`InjectedFailureError`）と検証エラー（`ValidationError`）は `Retry` の対象にしない。何度やり直しても同じ結果になるため。

**同じ定時の起動から実行が 2 つ始まることは防がない**（#92。2026-10-18 に判断）。起きうる経路と、防がない理由は次のとおり。

- **起きうる経路**: Scheduler の配信は少なくとも 1 回で、呼び出しに失敗すると上の表のとおりやり直す。定時の起動の実行名は、Scheduler が `StartExecution` の `name` で渡している（09「`dev` での検証結果」）。やり直しで同じ名前を使うなら、Standard の冪等性で 2 つ目の実行は始まらない。名前が変わるなら、別の実行がもう 1 つ始まる。実行名が違えば投入 Lambda の重複排除 ID（`<実行名>:<配信対象 ID>`）も違うため、メールが二重に送られる。**やり直しで同じ名前になるかは、公式に記述が無く、観測もしていない**（観測した 2 回はどちらも 1 回目で成功した）
- **防がない理由**: 実行名を起動ごとに決まった値にする手段が、Scheduler だけでは無い。universal target なら `StartExecution` の `name` を渡せるが、Scheduler が埋められる値のうち、予定の時刻（`<aws.scheduler.scheduled-time>`）は `:` を含んで実行名に使えず、`<aws.scheduler.execution-id>` は試行ごとに変わる（公式「Adding context attributes」）。値を変換するには、Scheduler とステートマシンの間に Lambda などを足す必要があり、元資料の構成から外れる。デモでは足さない
- **起きたときに分かること**: 同じ日に、定時の起動の実行（実行名が UUID）が 2 つ並ぶ。`list-executions` で見える
- 再試行の回数・時間（185 回・24 時間）は、`dev` で観測したサービスの既定と同じ値を明示したもので、挙動は変えていない。既定に頼ると、値がテンプレートに出ず UT で固定できないため明示した

**起動の失敗の通知**（#101。2026-10-20 に判断）: Scheduler がステートマシンを起動できなかった呼び出しは、DLQ を経て通知に乗せる。実行が始まらないため、状態変化イベントによる通知（F-5）には乗らない。

| 段 | 内容 | 管理 |
|---|---|---|
| DLQ | SQS の**標準**キュー（Scheduler は FIFO を DLQ に使えない。公式「Configuring a schedule's dead-letter queue」）。保持 4 日。Scheduler の実行ロールに、この DLQ への `sqs:SendMessage` だけを足す | Terraform |
| Schedule の `DeadLetterConfig` | 上の DLQ を指す | CDK |
| アラーム | DLQ の `NumberOfMessagesSent` の 5 分間の合計が 1 以上で `ALARM`。データの無い期間は `ALARM` にしない（`notBreaching`） | CDK |
| EventBridge rule | このアラームの `ALARM` への変化（`CloudWatch Alarm State Change`）を、Slack 通知 Lambda へ流す | CDK |

- **送信数で数え、メッセージ数では数えない**: DLQ のメッセージ数（`ApproximateNumberOfMessagesVisible`）で数えると、DLQ を空にするまで `ALARM` のままになる。アラームの通知は状態が変わったときだけなので、次の日の失敗が通知されない。送信数なら、届いた期間だけ `ALARM` になり、データが無くなれば `OK` に戻る（`local` で確かめた。09「LocalStack での検証結果」）。元資料の改善提案 1 は「DLQ のメッセージ数」だが、上の理由で送信数にした
- **通知が届くまでの時間**: 公式によると、Scheduler はやり直せるエラーなら `RetryPolicy`（上の表。最大 24 時間）を使い切ってから DLQ へ送る。**実行ロールの権限の誤り（`AccessDeniedException`）と、ステートマシンが存在しないこと（`StateMachineDoesNotExist`。削除・名前の変更）は、どちらもやり直されず、予定の時刻の約 46 秒後に DLQ へ届き、さらに約 3 分 12 秒後にアラームが `ALARM` になって通知された**（実 AWS の `dev`、2026-10-21、#101。09「`dev` での検証結果」）。スロットリング・Step Functions 側の障害がやり直されるかは未観測で、やり直されるなら通知は最大 24 時間後になる
- **原因は DLQ に残る**: 通知に入るのはアラーム名と `ALARM` になった理由だけ。起動に失敗した理由は、DLQ のメッセージの属性で確かめる。`ERROR_MESSAGE` に拒否したロール・アクション・ターゲットの ARN が、`SCHEDULED_TIME` にどの日の起動かが入る（実物は 07「Scheduler の DLQ のメッセージ」）
- **Schedule の無効化・削除は通知されない**: 呼び出しが起きないため DLQ にも届かない。気づく手段（その日の実行が無いことを検知する等）は #109 で決める
- **アラームの費用**: 標準の解像度のメトリクスのアラーム 1 つ（09「費用」）

**公式の推奨との違い**（#90。2026-10-18 に判断）: Lambda タスクの `Retry` は、公式の[ベストプラクティス](https://docs.aws.amazon.com/step-functions/latest/dg/sfn-best-practices.html)と CDK の既定（`retryOnServiceExceptions`）に合わせず、上の表のままにする。CDK の UT で対象を固定している。

| 項目 | 公式の推奨・CDK の既定 | このデモ | 理由 |
|---|---|---|---|
| `Lambda.ClientExecutionTimeoutException` | 含む | **含まない** | 呼び出しの応答を待ちきれなかった失敗で、関数に届いて動いたかが分からない。やり直すと二重に動きうる。`DataSync` では関数がもう 1 回起動し、データ連携が 2 回走りうる。判定できない失敗はやり直さず、`FAILED` にして通知に乗せる（`error-handling.md`「判定不能を正常値に丸めない」） |
| `Lambda.TooManyRequestsException` | 含まない | **含む** | スロットリングは、関数が動く前に Lambda が呼び出しを断った失敗。やり直しても二重にならず、時間を置けば通りうる |
| 回数・間隔 | 最大 6 回・2 秒・倍率 2 | 最大 2 回・2 秒・倍率 2 | 一時的なエラーが 2 回のやり直しで解消しなければ、実行を `FAILED` にして通知し、人が判断する。6 回にしても待つのは計約 2 分（2 + 4 + 8 + 16 + 32 + 64 秒）で、ステートマシンのタイムアウト（40 分）には収まる。回数の差は時間の都合ではなく、通知までの早さを選んだもの |

### 保持期間

| 対象 | 期間 | 理由 |
|---|---|---|
| SQS メッセージ | 1 日 | 試した直後に確認できれば足りる |
| DLQ メッセージ | 4 日（既定） | DLQ の中身を後から見られるよう、本キューより長く取る |
| Scheduler の DLQ メッセージ | 4 日（既定） | 起動に失敗した理由（エラーコード）を、通知を受けてから確かめられるようにする |
| S3 の連携ファイル | 7 日（ライフサイクルで削除） | 費用と残骸を抑える |
| CloudWatch Logs | 7 日 | 同上 |

## エラーハンドリング・堅牢性

| 状況 | 振る舞い |
|------|----------|
| 実行入力の `failAt` が未定義の値 | 投入 Lambda が `ValidationError` で失敗し、実行が `FAILED` になり通知が出る |
| 投入 Lambda の注入エラー | キューへ何も積まずに失敗し、実行が `FAILED` になり通知が出る |
| `SendMessageBatch` の一部失敗 | 失敗した ID をログに出して投入 Lambda を失敗させる。Retry で全件を送り直すが、重複排除 ID が決定的なため重複しない |
| Lambda の一時的なエラー | Step Functions の `Retry` で再実行する。尽きたら実行が `FAILED` になる |
| Consumer での失敗（注入・本文不正） | その 1 件だけを再配信させる。3 回で DLQ へ移る。**通知は出ない**（元資料のリスク 1） |
| データ連携の途中失敗 | 実行が `FAILED` になり通知が出る。前段の書き込み（S3 等）は残る（元資料のリスク 4） |
| データ連携 Lambda が結果を返せない（タスクトークンが読めない・`SendTaskFailure` も失敗した・関数が落ちた） | エラーログを出して終える。`DataSync` がハートビートかタスクのタイムアウトで失敗し、実行が `FAILED` になり通知が出る。待ち続けず、判定できない結果を成功にも丸めない |
| ステートマシンのタイムアウト | 実行が `TIMED_OUT` になり通知が出る |
| 手動での実行停止 | 実行が `ABORTED` になり通知が出る |
| 通知 Lambda が想定外のイベントを受けた | 何もせず正常終了し、警告ログを出す（誤ったイベントで再試行を繰り返さない） |

エラー時のログには、エラー名・メッセージ・スタックトレースを含める（`error-handling.md`）。

## 運用性

- **実行と確認は CLI で完結する**（03「操作方針」）。管理コンソールを開かなくても、02 の受け入れ条件をすべて確かめられること
- **どの処理のログかを絞り込める**: 構造化ログに `function`（関数名）・`executionName`（実行名）・`stub`（スタブ名）を含める。1 回の実行に属するログを `executionName` で横断して追える
- **削除で残骸を残さない**: CDK → Terraform の順で削除すると、S3 バケットも中身ごと消える（`dev` でも同じ）。ロググループは CDK の管理下に置いて一緒に消す
