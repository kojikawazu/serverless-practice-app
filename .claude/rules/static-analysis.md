# 静的解析の運用

使用するツールは各言語のコーディング規約（`typescript.md` / `go.md` / `java.md` / `ruby.md` / `python.md` / `php.md`）で定める。**GitHub Actions のワークフロー YAML は actionlint で検査する**（公式 Docker イメージをタグ固定で実行すると shellcheck も同梱され、`run:` の中身まで検査される）。**Markdown については、言語別の規約を持たないため本ルールが markdownlint の運用を直接定める**。本ルールは**どう運用するか**を定める。

## 役割分担（重ねない）

| 種類 | 役割 | 議論の対象 |
|---|---|---|
| **Formatter** | 見た目（インデント・改行・引用符）を機械的に統一する | **しない**。デフォルト設定に従う |
| **Linter** | バグの温床・危険なパターンを検出する | ルールの追加・除外のみ議論する |
| **型チェッカ** | 型の不整合を検出する | しない |

- **見た目に関する Linter ルールを有効にしない**。Formatter と競合し、直しても直らないエラーが発生する（TypeScript は ESLint なら `eslint-config-prettier`、oxlint なら `style` カテゴリを有効にしない、Python は ruff の format 系ルール除外などで無効化する）。
- **フォーマットの好みを議論しない・レビューで指摘しない**。Formatter の出力が正である。フォーマット指摘が出る状態なら、それは CI の設定不足である。

## CI で必須にする

- **Linter・Formatter・型チェックはすべて CI で実行し、違反があればマージをブロックする**。ローカル任意実行にしない。
- **警告（warning）を放置しない**。「警告は出るが動く」状態が常態化すると、新しい警告が埋もれて検出装置として機能しなくなる。**警告ゼロを維持**し、守れないルールは有効にしない（`error` にするか、無効にするかの二択）。
- Formatter は**差分ゼロを検証**する（`--check` / `--test` 系）。CI がコードを自動整形してコミットし返す運用にしない。
- 型チェックは**ビルドとは別に明示実行**する（TypeScript の `tsc --noEmit` 等）。バンドラの型スキップ設定で見逃さないため。

## markdownlint（Markdown の検査）

**Markdown はどのプロジェクトにも存在する**（README・設計書・`.claude/rules/`）。しかも Formatter を持たないため、検査を入れないと書式が書き手ごとにばらつく。「ルールで書式を定めているのに、それを検出する装置が無い」状態にしない。

| 対象 | 正本 |
|---|---|
| 対象ファイル・除外・有効ルール | `.markdownlint-cli2.jsonc` |
| 実行コマンドとバージョン | `scripts/lint-docs.sh`（CI も同じものを実行する） |

- **方針は「見た目は検査せず、壊れているものだけを検出する」**。行長（MD013）や表のパイプ揃え（MD060）を error にすると、内容と無関係な指摘が出続けて**警告が常態化し、検出装置として機能しなくなる**。
- **Formatter（Prettier 等）と役割を重ねない。** Markdown に Formatter を掛けているなら、空行・記号・折り返しは Formatter の領分であり、同じ観点の markdownlint ルールは無効にする。両方を有効にすると「直しても直らないエラー」が出る。
- **自前の検査スクリプトと役割が重なる場合は、担当を 1 つに決める。** 例: 見出しアンカーの実在を自前スクリプトで検査しているなら `MD051`（リンクフラグメント）は無効にする。両方が同じ観点を見ると、片方の誤検知を抑えるためにもう片方も緩めることになる。
- **無効化・緩和したルールは、設定ファイルに理由をコメントで書く**。理由の無い設定は、あとで誰も触れなくなる。
- **抑制コメント（`<!-- markdownlint-disable -->`）で回さず、書式側を直す**。`lessons-learned.md` が定める「小見出しは `###` を使う」は、この方針を前提にしている。

### `--fix` は本文を壊すことがある

**自動修正は「構文上そう見える」という推測で本文を書き換える。** 全ファイルへ一括適用したら、コミット前に必ず差分を読む。**違反件数の増減で判断しない**（壊れた箇所は新たな違反を生むため、件数は修正の正しさを示さない）。

| ルール | `--fix` が壊すもの |
|---|---|
| MD018（`#` の後の空白） | 行頭の issue 参照（`#123 では〜`）を「空白漏れの見出し」と誤検出し、`# 123 では〜` という H1 へ変換する |
| MD010（ハードタブ） | Go・Makefile のコード例のタブをスペースへ変換する（どちらもタブが正） |
| MD029（番号付きリスト） | 引用やコードブロックで分断されたリストの連番を振り直す（`3. 4.` → `1. 2.`） |

対処は「ルールを無効化する」「オプションで範囲を狭める（`MD010` の `code_blocks: false` 等）」「本文側を直す」のいずれか。**どれを選んだかを設定のコメントに残す。**

### 導入時に既存の違反が大量に出る場合

**除外リストで先送りしない。** 一度入れた除外は恒久化し、検出装置が形骸化する。次の順で、**同一 PR の中で 0 件にしてから CI を足す**。

1. 既定設定のまま実行し、**ルール別の件数を実測する**（どれを無効化すべきかは机上では決まらない）
2. 見た目に関するルールを無効化・緩和し、理由を設定に書く
3. `--fix` を適用し、**差分を読んで意味が変わった箇所を戻す**
4. 残りを文脈に応じて手で直す。**同じ違反コードでも正しい直し方は文脈で変わる**（例: 強調のみの行は、小見出しなら見出しへ、メタ情報なら強調を外し、引用句なら引用にする）
5. 違反 0 件を確認して CI を有効にする

## shellcheck（シェルスクリプトの検査）

`.sh` ファイルを 1 本でも持つなら、専用のレーンで検査する。**`.sh` は actionlint レーンでは検査されない。** actionlint が shellcheck へ渡すのはワークフローの `run:` の中身だけであり、独立したスクリプトは対象外になる。

検査・セットアップ・デプロイのスクリプトは CI の実体であることが多く、壊れた場合の実害は Markdown より大きい。

| 対象 | 正本 |
|---|---|
| 実行コマンドとバージョン | `scripts/lint-shell.sh`（CI も同じものを実行する） |
| CI での実行 | `.github/workflows/shellcheck.yml`（パスフィルタをかけず常時実行する） |

- **検査対象は `git ls-files --cached --others --exclude-standard -- '*.sh'` から引く。** ディレクトリの対象リストを持たない。対象リストで書くと、新しい場所にスクリプトを足したときに**黙って検査されなくなる**。
- **`--others`（未追跡ファイル）を含める。** これが無いと、コミット前の新規スクリプトが手元で検査されない。CI では全てコミット済みのため通ってしまい、**手元でだけ穴が空く**。
- **バージョンを固定する。** ランナーにプリインストールされた shellcheck はバージョンが固定できないため、手元の shellcheck が固定バージョンと一致しない場合は固定タグの Docker イメージへ倒す。**一致しないものを黙って使わない**（「手元で通ったのに CI で落ちる」の原因になる）。
- **`info` レベルの指摘も落とす。** 「警告ゼロを維持する」の対象に含める。守れないルールは抑制ではなく、**書き方を変えて解消する**（例: `ls` の出力を数える SC2012 は `find` に置き換える）。

### 行頭を `# shellcheck` で始めない

**コメント行の行頭が `# shellcheck` だと、内容にかかわらず抑制ディレクティブとして解釈される。** 日本語で `# shellcheck 自体は〜` と書いても同じで、`SC1072` / `SC1073`（Couldn't parse this shellcheck directive）で**エラーとして落ちる**。

ツール名を文頭に置きたくなる場面は多いので、**語順を変えるか、文の途中に置く**。これは抑制の話ではなく**構文の話**なので、抑制コメントの作法（後述）では回避できない。

## 秘匿ファイルの混入検出

**鍵・`.env` などの秘匿ファイルが Git 管理下に入った時点で CI を落とす。** Linter ではないが、「CI 必須・コマンドはスクリプト 1 箇所・常時実行」の運用は本ルールの他の検査と同じである。

| 対象 | 正本 |
|---|---|
| 検出パターン・除外パターン・実行コマンド | `scripts/check-secret-files.sh`（CI も同じものを実行する） |
| CI での実行 | `.github/workflows/secret-scan.yml`（パスフィルタをかけず常時実行する） |

- **`.gitignore` は検出の代わりにならない。** `.gitignore` が効くのは未追跡ファイルだけで、一度追跡されたファイル・`git add -f`・書き漏れには効かない。`.gitignore` は「混入させない」側、本検査は「混入したら落とす」側であり、**両方を置く**。
- **push 済みの秘匿ファイルは、追跡から外しても消えない。** Git の履歴は追記型で、`git rm --cached` しても過去のコミットに残る。**対処は鍵・トークンのローテーションしかない**（履歴の書き換えは、既に取得された複製を消せない）。だから検出は push の前、遅くとも PR の時点で行う。
- **未追跡のファイルも検査対象に含める**（`git ls-files --others --exclude-standard`）。`.gitignore` に書き忘れた `.env` を、コミットする前に手元で捕まえられる。CI では全てコミット済みのため結果は変わらない。
- **git 管理外ではエラーで止める。** 「追跡されているもの」が定義できない状態で 0 件と報告すると、検査していないのに成功扱いになる。
- **テンプレートと型定義は除外する**（`*.example` / `*.sample` / `*.template` / `*.dist` / `*.env.d.ts`）。それ以外で正当に管理したいファイルがある場合は、スクリプトの除外パターンへ**ファイル単位で最小に**足し、理由をコメントで書く（抑制コメントの作法と同じ）。
- **本検査は履歴を走査しない。** インデックスを読むだけなので数秒で終わる反面、**導入前に混入したものは見つからない**。導入時に一度だけ、同じパターンで履歴上の全パスを照合する（パターンを書き写さず、スクリプトのオプションで切り替える）。

  ```bash
  ./scripts/check-secret-files.sh --history
  ```

  ヒットした場合は、**そのファイルが含んでいた鍵・トークンをローテーションする**。履歴からの削除だけで済ませない。

## 抑制コメントの扱い

`eslint-disable` / `# noqa` / `//nolint` / `@SuppressWarnings` / `@ts-expect-error` / `<!-- markdownlint-disable -->` などの抑制は、**例外的な手段**として扱う。

- **理由をコメントで必ず書く**。「なぜこのルールを守れないのか」「いつ解消できるのか」を書く。理由のない抑制は差し戻す。
- **範囲を最小にする**。ファイル全体ではなく**該当行のみ**を抑制する。ファイル先頭での一括無効化をしない。
- **抑制するルールを明示する**（`eslint-disable-next-line no-console` のように**ルール名を書く**）。ルール名なしの全ルール抑制をしない。
- `@ts-ignore` ではなく **`@ts-expect-error` を使う**（問題が解消したとき「不要な抑制」として検出されるため、抑制が残り続けない）。
- 同じ抑制が**何箇所にも増えたらルール設定自体を見直す**。プロジェクトの実態に合っていないルールを、抑制コメントで回し続けない。

## ルール設定の変更

- **ルールの追加・除外はプロジェクト全体の合意で行い、設定ファイルに理由をコメントで残す**。個人の好みで一時的に緩めない。
- 既存プロジェクトへ厳しいルールを導入して大量の違反が出る場合、**一括抑制せず段階導入する**（対象ディレクトリを限定する、新規コードのみ対象にする、期限を決めて解消する）。
- 設定ファイル（`.eslintrc` / `.golangci.yml` / `pyproject.toml` / `.markdownlint-cli2.jsonc` 等）は**コミット対象**。ローカル固有設定に依存しない。

## エディタ・コミット時

- **エディタの保存時フォーマットを有効にする**（CI で落ちる前に手元で解決する）。
- pre-commit フックを使う場合は**高速なもの（変更ファイルのみの format / lint）に限定**する。テストや全体型チェックを含めるとコミットが重くなり、`--no-verify` が常態化する。
- **フックは CI の代替にならない**。スキップ可能なため、最終的な担保は必ず CI に置く。

## レビュー観点

- 抑制コメントに理由が書かれているか。範囲・ルール名が最小限に絞られているか。
- Formatter が直すべき見た目をレビューで指摘していないか（＝設定不足のサイン）。
- 警告が出たまま放置されていないか。
- 無効化したルールの理由が設定ファイルに書かれているか。
- `--fix` の結果を読まずにコミットしていないか（意味が変わった箇所が無いか）。
- **秘匿ファイルの検出（`scripts/check-secret-files.sh`）の除外パターンが、理由なく広げられていないか**（既定の除外（テンプレート・型定義）以外に、ディレクトリ単位・拡張子単位の除外を足していないか）。
