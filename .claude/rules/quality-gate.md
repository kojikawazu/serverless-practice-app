# 品質ゲート

- **セルフレビュー必須**: 要求仕様の作成・ドキュメント生成・設計・実装が完了したら、次のフェーズに進む前にセルフレビューを実施する。
- **セルフレビュー後の修正**: セルフレビューで指摘を検出したら、修正まで実施する。
- **設計完了時**: 要求仕様との齟齬がないか確認し、ユーザーにレビューしてもらう。レビュー完了まで実装に進まない。
- **実装完了時**: 設計仕様との齟齬がないか確認し、ユーザーにレビューしてもらう。

## 検査は壊して確かめる

検査（テスト・Lint ルール・CI の検査ステップ・検査スクリプト）の価値は、**壊れたものを落とせること**で決まる。通ったという事実だけでは、検査が働いているのか、何も見ていないのかを区別できない。

- **追加・変更したら、対象をわざと壊して失敗することを確かめる。** 赤くなるのを一度見るまで「検査が入った」とみなさない。
  - テスト: 実装を一時的に壊す（条件を反転する・戻り値を差し替える）
  - Lint ルール: 違反するコードを書く
  - CI のステップ・検査スクリプト: 検出対象を置く、前提を崩す（未追跡ファイル・対象 0 件・別のシェルやバージョンで実行する）
- **合否を判定するコマンドをパイプに通さない。** パイプラインの終了コードは最後のコマンドのものになるため、`| tail` を付けただけで失敗が成功に変わる。出力を絞りたいなら、出力を捨てて終了コードを明示的に確かめる（`cmd >/dev/null 2>&1; echo "cmd=$?"`）か、`set -o pipefail` を付ける。
- **「0 件が正常」の検査で `grep` の終了コードをそのまま使わない。** `grep` は一致 0 件で 1 を返すため、`set -e` の下では正常系で落ち、`!` で反転すると grep 自体のエラーまで成功になる。件数を数えて比較する。
- **「対象が 0 件」と「検査して 0 件」を区別する。** 対象の列挙が空になったら、合格ではなく失敗として扱う。列挙の失敗は、何も検査せずに緑になる。
- **「通った」と報告する前に、各コマンドの終了コードが 0 であることを確かめる。**

終了コードが呼び出し側に届かない検査は、失敗しても緑のままになる。検出装置が黙って止まっていることは、壊してみるまで分からない。
