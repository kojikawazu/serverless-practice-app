# 外部サービスの値は観測してから書く

**外部サービスが作る値・返す値は、動かして観測するまで分からない。** 公式の記述・名前の知識・別の観測からの推論で書いた値は、観測した値と同じ書き方で残すと、誤りが仕様として定着する。仕様書を読む人も、通知や分岐を作る人も、書かれた値を観測済みとして扱うためである。

本ルールは、観測した値と推論した値を**書き分ける**ことで、推論の誤りが仕様に入るのを防ぐ。

## 対象

外部サービス（AWS・LocalStack・SaaS の API）が作る・返す値を、次のどこかに書くとき。

- 仕様書・ガイド（`docs/`）
- 検証結果の記録（09「`dev` での検証結果」など）
- テストの偽物（偽の CLI・偽の API の応答）
- コードのコメント

特に誤りやすいのは次の値である。

| 種類 | 例 |
|---|---|
| エラー名 | `States.Timeout` / `States.HeartbeatTimeout` |
| 出る場所 | 実行の結果か、実行履歴のイベントか、状態変化イベントか |
| 項目の有無 | `null` が入るのか、項目そのものが無いのか |
| 名前・ID の形と付ける側 | 実行名を付けるのは呼び出し側か、サービスか |
| 既定値の扱い | 既定値の項目を応答に含めるのか、省くのか |

自分のコードが作る値は対象外とする（コードとテストが正本になる）。

## 観測した値には出どころを添える

**観測した値には、観測した API と項目、観測した環境を添える。** 値の名前を知っていても、どこに出るかは知らないことがある。出る場所は値ごとに違う。

- **API と項目**: `describe-execution` の `error`、`GetExecutionHistory` の `TaskTimedOut` イベントの `error` のように、項目まで書く
- **環境**: LocalStack か実 AWS か
- **いつ・どの作業で**: 日付と issue 番号

```text
❌ TIMED_OUT の実行のエラー名は States.Timeout
   → 名前は実在するが、実行の結果（describe-execution）には error の項目そのものが無かった

✅ TIMED_OUT の実行は、describe-execution の結果に error / cause が無い。
   States.Timeout は実行履歴の最後のイベント ExecutionTimedOut の error にだけ出る
   （実 AWS、2026-10-13、#44）
```

## 観測していない値は「未観測」と書く

**観測していない値は「未観測」と書き、出どころ（公式のどのページか）を添える。** 公式の記述は、1 ページ読んだだけでは揺れに気づけない。

- **公式の記述が揺れているときは、両方を書く**（どのページがどちらの値を書いているかも添える）
- **未観測と書いたら、観測する issue を立てる。** 「未観測」のまま誰も確かめない状態を残さない
- **受け取る側のコードは、未観測の値を当てにしない。** `null` と項目の欠落の両方を受け付けるなど、どちらでも壊れない作りにする（`error-handling.md`「判定不能を正常値に丸めない」）

```text
❌ ハートビート切れのエラー名は States.HeartbeatTimeout
   → 公式のエラー処理のページから書いた。Task ステートのページは States.Timeout と書いており、
     LocalStack で観測すると States.Timeout だった

✅ ハートビート切れのエラー名は未観測。公式のエラー処理のページは States.HeartbeatTimeout、
   Task ステートのページは States.Timeout と書いている（観測する issue: #<番号>）
```

## LocalStack の値を実 AWS の値として書かない

**LocalStack で観測した値は、LocalStack の値として書く。** LocalStack は実 AWS を再現しきれず、同じ操作で違う値を返すことがある（09「LocalStack での検証結果」）。

- 実 AWS で観測していないなら、実 AWS の値は「未観測」と書く
- 両方で観測した値は、環境ごとに分けて書く（同じ値だった場合も「両方で同じ」と書く）

## 推論を観測と同じ書き方で書かない

**確かめたことと、そこから推論したことを、同じ文体（断定）で書かない。** 直前の観測が懸念を裏付けると、残りも確かめたつもりになりやすい。

- **1 文ごとに「確かめた / 確かめていない」を分ける。** 確かめていないものには「〜しうる」「試していない」と書き、何から推論したかを添える
- **公式の記述を組み合わせた推論も推論である。** 公式の 2 つの記述がそれぞれ正しくても、2 つを結ぶ規則は推測であり、観測すると逆になることがある
- **数値（時刻の差・回数）は、書く前に元の記録から計算し直す。** 印象で書かない

```text
❌ 定時の起動の実行名は Step Functions が付けている
   → 公式の記述を組み合わせた推論。CloudTrail で観測すると、Scheduler が StartExecution の name で渡していた

✅ 定時の起動の実行名を付けた側は未観測。（推論の根拠）から Step Functions の可能性があるが、
   CloudTrail の StartExecution の requestParameters.name で確かめる
```

## 1 つ直したら、同じ方法で書いた値を洗い出す

**観測しないまま書いた値の誤りを 1 つ直したら、同じ方法・同じ時期に書いた他の値も洗い出して観測する。** 同じ書き方をした値は、同じ誤りを含みうる。1 件だけ直して終えると、残りが仕様に残り続ける。

洗い出した値と、観測の結果（または未観測として残した理由）を PR に書く。

## テストの偽物は観測した応答の形で作る

**外部サービスの偽物（偽の CLI・偽の API）は、実物の応答を一度観測してから、その形で返すように作る。** 渡した値をそのまま返す偽物は「実物はこう返すはず」という推測であり、既知の差分しか再現できない。未知の差分（既定値の項目を省くなど）は、偽物の上では起こらない。

- **観測できない段階で作るなら、偽物の冒頭に「推測で作った」と書く。** 実物で初めて動かしたときに、応答を偽物と突き合わせる
- **偽物を実物に合わせたら、実装を直す前にテストが落ちることを確かめる**（`quality-gate.md`「検査は壊して確かめる」）
- 往復の検査（作った値を読んで一致を見る）は、偽物が値を保つ限り必ず通る。偽物の形が正しいことの根拠にしない

## レビュー観点

- 外部サービスの値に、観測した API・項目・環境が添えられているか。添えられていないなら「未観測」と書かれているか。
- 「未観測」の値に、出どころ（公式のページ）と、観測する issue があるか。
- LocalStack で観測した値が、実 AWS の値として書かれていないか。
- 検証結果の断定文の 1 つずつに、根拠になった観測があるか（推論が断定で書かれていないか）。
- 誤りを 1 つ直した PR で、同じ方法で書いた他の値を洗い出した記録があるか。
- テストの偽物が、観測した応答の形で作られているか。推測で作ったなら、その旨が偽物に書かれているか。
