# 教訓の記録

同じ誤りを二度繰り返さないために、**得られた教訓を `docs/lessons-learned.md` に追記して蓄積する**。記録は「あとで読み返して行動が変わる」ことを目的とし、感想文にしない。

- **正本の置き場所**: 教訓の本文は `docs/lessons-learned.md` に集約する。他のドキュメントへ本文を複製しない。
- **追記のみ**: 過去のエントリは書き換えない。認識が後から変わった場合は、新しいエントリを追記して古いエントリから参照する（履歴として残す）。
- **新しいものを上に**: ファイル先頭（見出し直下）に追記する。古い教訓を掘り返さなくても最新が読める状態を保つ。
- **AI エージェントも記録する**: 下記トリガーに該当したら、指示を待たずに追記を提案する。ユーザーが不要と判断した場合は記録しない。

## 記録するトリガー

以下に該当したら記録する。**該当しないものは記録しない**（何でも書くとファイルが読まれなくなる）。

| トリガー | 記録するタイミング | 例 |
|---|---|---|
| 事故・障害・データ破壊が起きた | 復旧が済み、根本原因が判明した時点 | 本番データの消失、デプロイ事故、環境変数の取り違え |
| レビュー指摘・修正で自分の誤りが判明した | 修正が完了した時点 | セルフレビュー・Codex / Copilot レビューで見つかった設計・実装の誤り |
| ハマって時間を溶かした | 原因が判明した時点（解決前に書かない） | 環境・設定・ライブラリ挙動が原因で長時間詰まったケース |

**記録しないもの**: 単発のタイプミス、その場限りの試行錯誤、コードやコミット履歴を読めば分かること、まだ原因が分かっていない事象（原因判明まで待つ）。

## 記録フォーマット

1 件 = 1 ブロック。**表形式にはしない**（教訓は文脈を伴うため、セルに収めると意味が落ちる）。

```markdown
## YYYY-MM-DD タイトル（何が起きたかが一読で分かる一文）

### 概要

何が起きて何が問題だったかを 1〜3 行で。ここだけ読んで内容が掴める粒度にする。

### 詳細

- 何が起きたか: 事象・影響範囲（対象データ・ユーザー・期間）
- なぜ起きたか（根本原因）: どのコード・設定・判断が原因か。表層の症状で止めない
- 教訓 / 次からどうする: 次に同じ状況でとるべき具体的な行動。「気をつける」は書かない
- 関連: 関連するルールファイル・PR・issue・コミットへの参照
```

**小見出しは `###` を使い、`**概要**` のような強調文字列を見出し代わりに置かない**。markdownlint の MD036（no-emphasis-as-heading）に抵触し、エントリを追記するたびに違反が増える（空行を詰めて回避すると今度は MD032 に抵触する）。抑制コメントで回し続けず、書式側を見出しに揃える。

各項目の書き方:

- **タイトル**: 「バグ修正」のような分類名ではなく、事象そのものを書く（例: `E2E のテスト DB 接続先が本番に解決された`）。
- **根本原因**: 「〇〇を修正した」は対処であって原因ではない。「どの条件で何がどう振る舞った結果、何が起きたか」を書く。
- **教訓**: 再現可能な行動に落とす。「テスト用の接続先は専用の環境変数のみを参照し、フォールバックを書かない」のように、次回そのまま従える形にする。
- **関連**: 教訓がルール化された場合は、そのルールファイルを必ず参照に入れる。

## 教訓をルールへ昇格させる

同じ教訓が繰り返し現れる、または恒久的に守るべき制約になったものは、`.claude/rules/` の該当ファイルへ **ルールとして追記する**。その場合も `docs/lessons-learned.md` のエントリは消さず、「関連」にルールファイル名を追記する。

**「繰り返し現れる」の観測範囲はこのリポジトリ内に閉じない。** 他リポジトリで同じ失敗が起きている場合も昇格の対象であり、その検出は集約先が担う（後述「横断集約との関係」）。

判断の目安:

| 状態 | 置き場所 |
|---|---|
| 一度きりの学び・文脈依存の知見 | `docs/lessons-learned.md` のみ |
| 今後も常に守るべき制約になった | `.claude/rules/` に追記し、教訓側から参照する |
| 特定機能の仕様・設計判断 | `docs/design/` 配下（教訓ではなく設計判断として書く） |

## 横断集約との関係

本ファイルは**このリポジトリの教訓の正本**である。別途、複数リポジトリの教訓を機械的に収集する集約先（`my-lessons-learned`）があり、本ファイルはその収集元になる。

- **集約先は一方向の派生である。** 本ファイルから集約先へコピーされるだけで、逆流はしない。
- **集約先を手で編集しない。** 誤字や書式を集約先で直しても、次回の収集で上書きされて消える。直すべきは常に本ファイル側である。ただし本ファイルも「追記のみ」であるため、誤りが判明した場合は新しいエントリを追記して古いエントリから参照する。
- **「他のドキュメントへ本文を複製しない」条項は、人が書く複製を禁じるもの**であり、機械的・一方向・再生成可能な派生は対象外とする。両者の違いは「片方を直したらもう片方も直さねばならないか」にある。派生は再生成すれば追従するため、二重管理にならない。
- **書式を崩さない。** 集約側は `## YYYY-MM-DD タイトル` / `### 概要` / `### 詳細` の構造でパースする。見出しレベルや順序を変えると、そのエントリは収集されないか壊れた形で収集される。**書式の逸脱は収集時にエラーにならず、静かに取りこぼされる**ため気づきにくい。

集約先でのタグ付与・ダイジェスト生成・昇格候補の検出は `/lessons-sync` スキルが担う。本ファイルの書き手が意識すべきことは**書式を守ること**だけでよい。

## 関連ルールとの分担（重複させない）

| 観点 | 担当 |
|---|---|
| 誤り・失敗から得た教訓の蓄積（本ファイル） | `lessons-learned.md` |
| 恒久的に守るべき制約そのもの | `.claude/rules/` の各ルールファイル |
| PR 単位の原因・再発防止の記述 | `pr-description.md`（バグ修正の「原因」「再発防止」） |
| 機能の設計判断・トレードオフ | `docs/design/` 配下の設計ドキュメント |
| ドキュメント更新の完了条件 | `documentation.md` |
| 複数リポジトリ横断での教訓の集約・タグ付与・昇格候補の検出 | `/lessons-sync` スキル（集約先リポジトリ `my-lessons-learned`） |
