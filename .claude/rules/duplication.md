# 重複と共通化

**重複は「同じコードが 2 つある」ことではなく、「同じ知識が 2 箇所にある」こと。** 片方を直したらもう片方も必ず直さねばならない関係にあるものだけが、共通化すべき重複である。

## 共通化する / しないの判断

| 状況 | 判断 |
|---|---|
| 同じ**業務ルール・仕様**が複数箇所にある（税率計算、ステータス遷移条件、権限判定） | **共通化する**。仕様変更時の直し漏れが即バグになる |
| 同じ**リテラル値**が複数箇所にある（上限値・API パス・キー名） | **定数化して共有する**（各言語のコーディング規約「定数の配置」に従う） |
| 同じ**検証内容**が複数レイヤにある | **共通化する**。担当レイヤを 1 つに決める（各スタックの API ルール「バリデーションの二重定義禁止」に従う） |
| 形は同じだが**変わる理由が違う**（偶然の一致） | **共通化しない**。片方だけ変更したい日が必ず来る |
| **信頼境界をまたぐ**（フロントとバックエンドの入力検証） | **重複させる**。ただし定数・スキーマは共有できるなら共有する |
| **層をまたぐ型**（DTO とドメインモデル、DTO と DB エンティティ） | **共通化しない**。似ていても変更理由が違う（API 契約 / 業務 / 永続化）。共通化すると内部スキーマが API に漏れる |
| テストの**期待値・ケース内容** | **共通化しない**。テストは重複してでも読んで分かることを優先する（セットアップの共通化は可） |
| 環境の**初期化手順**が README・Makefile・CI に書き分けられている | **1 つのスクリプトに寄せる**。CI もそれを実行し、手順が壊れたら CI が落ちる状態にする（後述） |

## 早すぎる共通化をしない

- **2 回目までは重複を許容し、3 回目で共通化する**。2 箇所では「同じ知識」なのか「たまたま同じ形」なのか判別できない。
- 共通化した結果 **`if` / フラグ引数で分岐が増えるなら、それは共通化すべきでなかった**サイン。分けて書き直す。
- 「将来使うかもしれない」ための抽象化を作らない。**今 3 箇所で使われている事実**だけを根拠にする。
- 判断に迷ったら**重複を残す**。重複は後から共通化できるが、間違った共通化を剥がすのは高くつく。

## 共通化するときの置き場所

- 置き場所は**参照範囲**で決める（型・定数と同じ判断軸）。1 箇所に閉じるならその場、モジュール内なら当該モジュール、複数モジュールから参照されるなら共有層へ。
- **`common` / `util` / `helper` を「とりあえずの置き場」にしない**。無関係な処理の集積になり、全モジュールがそこへ依存して**レイヤの一方向依存が壊れる**。名前が付けられない＝共通化の単位が間違っている。
- 共通化した先が上位レイヤになってはならない。**共通化は必ず下位（または同位の共有層）へ抽出**する。

## 環境の初期化手順を二重管理しない

**開発環境の初期化手順も「同じ知識」である。** README・Makefile・CI ワークフローに書き分けると、必ずどれかが腐る。

コードの重複と違い、**手順の重複は壊れても誰も気づかない**。CI は README を読まないため、**README が間違っていても CI は緑のまま**になる。検知する仕組みが構造的に存在しない。

- **初期化手順は 1 つのスクリプトに置き、ローカルと CI の双方がそれを実行する。**
  - **README には「そのコマンドを叩く」ことだけを書く**（手順の中身を書かない）
  - **Makefile / タスクランナーのターゲットは、スクリプトを呼ぶだけにする**
  - **CI もそのスクリプトを実行する。** これにより**手順が壊れたら CI が落ちる**。README だけが腐る状態を、規律ではなく構造で防ぐ
- **初期化スクリプトは冪等にする。** 何度実行しても、既存の設定値・データを壊さない。

**「3 回目で共通化する」は手順には適用しない。** あの基準は「同じ知識なのか、たまたま同じ形なのか」がコードでは 2 箇所では判別できないために置いている。手順は**2 箇所でも同じ知識であることが最初から明らか**で、しかもズレても検知されない。**1 箇所目から共通スクリプトに置く。**

### CI の手順をそのままローカルへ持ち込まない

**CI は「毎回チェックアウトが新品」を前提に書かれている。その前提はローカルでは成立しない。**

スクリプトを 1 本に寄せる際、CI 側のコマンドをそのまま移すと**ローカルでだけ破壊的になる**。

```text
悪い例: CI の記述をそのまま make setup へ持ち込む
  アプリケーションキーを無条件に再生成する
  → CI は毎回 .env が新規なので無害
  → ローカルでは再実行のたびに鍵が変わり、
     既存セッションと暗号化済みデータが復号できなくなる

良い例: 未設定のときだけ生成する
  → CI では .env が常に新規なので結局毎回生成され、挙動は変わらない
```

**「新品なら同じ結果になる」処理でも、既存環境では破壊的になり得る。** 鍵・証明書の再生成、DB のリセット、マイグレーションのやり直し、依存ディレクトリの削除は特に注意する。**冪等性は「CI で通ること」では検証できない。**

## レビュー観点

- コピー＆ペーストの痕跡（同じ条件式・同じマジックナンバー・同じ変換処理）が 3 箇所以上にないか。
- 逆に、**共通化されたものにフラグ引数や分岐が増え続けていないか**（過剰共通化の兆候）。
- 共通化の置き場が `common` / `util` に流れ込んでいないか。
- **初期化手順が README・Makefile・CI に書き分けられていないか。** また **CI が実際にその共通スクリプトを実行しているか**（実行していなければ、手順が壊れても検知されない）。
- 初期化スクリプトが**再実行で既存の設定値・データを壊さないか**（鍵の再生成・DB リセット・依存の削除）。
