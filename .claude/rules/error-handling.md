# エラーハンドリング

- **バリデーション必須**: ユーザー入力・外部入力は必ずバリデーションする。
- **ドメイン層の制約**: ドメインモデル・値オブジェクトの不変条件は、コンストラクタ/ファクトリで弾く。**プログラム内部の誤り**（バッチ・別経路からの生成）に対する防御。
- **入口の検証**: リクエストの形式・型チェックは、ハンドラー/コントローラー層のスキーマで検証する。**ドメイン層で弾けることを理由に省略しない**（信頼境界での防御とエラー形式の統一は入口の役割で、ドメイン層では代替できない）。両者の関係と、制約の定義を 1 箇所に保つ方法は `domain-layer.md` を参照。
- **HTTP ステータスコード**: 適切なステータスコードで返す（400/401/403/404/500）。
- **統一エラーレスポンス**: エラーレスポンスの JSON 構造を統一する。
- **ログ**: エラー時はスタックトレースを含むログを出力する。センシティブ情報はログに含めない。

## 判定不能を正常値に丸めない

取得・判定の結果は「あり / なし / 判定不能」の 3 つの状態を持つ。**判定不能を「なし」「0 件」「不許可」と同じ値で表さない。** 同じ値にすると、壊れていることが結果から区別できなくなり、障害が正常として報告され続ける。

- **取得の失敗は「該当なし」として扱わない。** 外部ソースに到達できない・応答が壊れている場合は、「調査不能」として明示的に返す・記録する
- **判定できないときは安全側に倒す。** 例: 変更判定に失敗したらビルドを実行する、権限判定に失敗したら「判定できなかった」と区別して扱う。`|| true` で失敗を握り潰して「変更なし」にしない
- **判定不能になったことを検知できるようにする。** 調査不能が続いていることに誰も気づけない状態を作らない（件数の監視・失敗時の異常終了）
