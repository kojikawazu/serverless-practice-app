# IaC（Infrastructure as Code）

**state を失うと、既存リソースを認識できないまま `apply` することになる。** 重複作成・不整合を招き、復旧には既存リソースを 1 つずつ `import` し直す作業が必要になる。本ルールはその事故を構造で防ぐ。

## state はリモート backend に置く

**state をローカルファイルだけに置かない。** リモート backend（GCS / S3 等）を必ず設定する。

- `.gitignore` に `terraform.tfstate` を入れる**だけで終わらせない**。除外は正しいが、それは「どこに置くか」まで決めて初めて完結する。
- ローカル state は、**環境の入れ替え・PC の故障・リポジトリの再クローンで失われる**。
- **backend 設定そのものはコミットする**（`backend` ブロックは秘密情報ではない）。

| ファイル | Git | 置き場所 |
|---|---|---|
| `*.tf`（定義） | コミットする | リポジトリ |
| `backend` 設定 | コミットする | リポジトリ |
| `terraform.tfstate` | **除外する** | **リモート backend** |
| `terraform.tfvars` | **除外する**（秘密を含む） | 各自のローカル + **変数名の一覧をドキュメント化** |

**除外するファイルは、必ず「代わりの置き場所」とセットで決める。** `.gitignore` の判断を「秘密かどうか」だけで行うと、**秘密ではないが共有が必要なもの（state）が行き場を失う**。

### state を Git で管理してはならない理由

private リポジトリであっても選ばない。アクセス制御以外の問題が残るため。

| 問題 | 内容 |
|---|---|
| シークレットの永続化 | state には変数値が**平文で記録される**。Git 履歴からは消せず、キーをローテーションしても過去の値が残る |
| ロックが無い | Terraform は `apply` 中に state をロックする。Git にロックは無く、**同時 apply で壊れる** |
| マージ不能 | 巨大な JSON が毎回変わる。コンフリクトしても**手でマージしてはならない** |
| push 忘れ | コミットし忘れれば、ローカルのみと同じ結果になる |

## state の置き場所と prefix

**1 つの共有バケットを prefix（ディレクトリ）で分ける。prefix は「リポジトリ名」とする。**

```text
gs://kojikawazu-tfstate/
├── serverless-practice-app/          ← リポジトリと 1:1
└── <other-repo>/
```

```hcl
terraform {
  backend "gcs" {
    bucket = "kojikawazu-tfstate"
    prefix = "serverless-practice-app"
  }
}
```

- **リポジトリ名をそのまま使う。** 略称や別名を作らない（どの state がどのリポジトリのものか、名前だけで一意に分かる状態を保つ）。
- 1 リポジトリで環境を分ける場合のみ `serverless-practice-app/<env>` とする。**環境が 1 つなら階層を増やさない**。
- **prefix を後から変えない。** 変えると Terraform は「別の state」と認識し、既存リソースを見失う。

### prefix は権限境界ではない

**オブジェクトストレージの権限はバケット単位が基本**（GCS の均一バケットレベルアクセス等）。

> **バケットへの read 権限を渡した相手は、prefix に関係なく全プロジェクトの state を読める。**

state には認証情報が平文で含まれる。**特定のプロジェクトだけを他人と共有する予定があるなら、そのプロジェクトは別バケットに分ける。**

### state バケットに必要な設定

| 設定 | 理由 |
|---|---|
| **バージョニング有効** | **壊れた上書きから戻せる唯一の手段**。削除はソフト削除で戻せるが、上書きは戻せない |
| アクセス制御の一本化 | ACL を使わず IAM（またはバケットポリシー）に統一する |
| 公開アクセスの明示的な禁止 | 「既定に従う」ではなく enforced 相当にする |
| 古い版のライフサイクル削除 | バージョニング有効のまま版が無限に積もるのを防ぐ。**直近の履歴は残す条件**にする |

**state バケットは Terraform で管理しない。** 自分の state を保管するバケットを自分で作ると鶏と卵になる。**冪等なスクリプトで作成し、その手順をリポジトリに残す**（`duplication.md` の「初期化手順は 1 つのスクリプトに寄せる」）。

## 「壊れても誰も気づかない」状態を作らない

**IaC が実際の変更経路から外れていると、state が失われても何も壊れず、誰も気づかない。**

- デプロイや設定変更を IaC 以外の経路（CLI コマンド・CI の直接操作・管理コンソール）で行っている場合、**IaC は「適用されない定義」になる**。乖離は、次にインフラを変更しようとした瞬間に初めて表面化する。
- **どの変更をどの経路で行うかを決めて文書化する。** 経路が複数あるなら、**どちらが正か**を明記する。
- 同じ設定を 2 箇所（例: サービス側の環境変数と、イメージに焼いた `.env`）で持たない。持つなら**優先順位を明記**する（`duplication.md`）。

これは `duplication.md` の「CI は README を読まないので、README が腐っても CI は緑のまま」と同じ構造である。**検知する仕組みが無い乖離は、規律ではなく構造で塞ぐ。**

## 適用前の確認

- **`plan` の差分が空であることを定期的に確認する。** 差分が出るなら定義と実態が乖離している。
- **state を失った状態で `apply` しない。** 復元（`import`）が先。
- 破壊的な差分（`destroy` / `replace`）が出たら、**何が消えるかを読んでから**実行する。本番リソースの削除を伴う場合は `production-data.md` の手順にも従う。

## レビュー観点

- backend 設定がコミットされているか。ローカル state のままになっていないか。
- `.gitignore` で除外したファイルについて、**代わりの置き場所が決まっているか**（state はリモート backend、tfvars は変数名一覧のドキュメント）。
- prefix がリポジトリ名と 1:1 になっているか。後から変えていないか。
- state バケットのバージョニングが有効か。
- IaC が実際の変更経路に乗っているか。乗っていないなら、その旨と理由が記録されているか。
- 同じ設定が IaC と別経路の両方で管理されていないか。あるなら優先順位が明記されているか。
