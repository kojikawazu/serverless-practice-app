# PR 本文（初回コメント）の必須セクション

PR の初回コメント（PR 本文）は、レビュアーが**差分を読む前に判断材料を揃えられる**状態にする。変更種別ごとに必須セクションを固定し、省略しない。

## 共通ルール

- **変更種別を最初に宣言する**: `バグ修正` / `仕様変更` / `仕様追加` / `新規開発` / `ドキュメント` のいずれかを本文冒頭に書く。複数にまたがる場合は主たる種別を選び、従の内容は「概要」に書く（1 PR に複数種別を詰め込まない方が望ましい）。
- **`ドキュメント` 種別はドキュメントのみを変更する PR に限る**: **コード変更を含む PR は、ドキュメントを同時に更新していても `ドキュメント` 種別にしない。** コード側の種別（バグ修正 / 仕様変更 / 仕様追加 / 新規開発）を選び、ドキュメントの更新は「ドキュメント」セクションに書く。これを崩すと「docs も触ったから docs 種別」という逃げ道になり、`documentation.md` の「同一 PR でドキュメントを更新する」完了条件が形骸化する。
- **セクションは省略しない**: 該当がない場合も見出しを残し、`なし（理由）` と書く。空欄・見出しごと削除は不可。
- **原因欄に対処を書かない**: 「原因」は事象が起きたメカニズム、「方針」は直し方。`〇〇を修正した` は原因ではない。
- **受け入れ基準は検証可能な条件で書く**: 「正しく動く」ではなく「〇〇の状態で △△ すると □□ になる」と、レビュアーが再現・確認できる粒度で書く。
- **関連 issue は必ず参照する**: `Closes #<番号>`（バグ修正は `Fixes #<番号>`）を書く。運用の詳細は `github-issue.md` を正本とする。
- **差分から読めることを繰り返さない**: ファイル一覧の羅列ではなく、**なぜ**そう変えたかを書く。

## 全種別で必須のセクション

| セクション | 書く内容 |
|---|---|
| 変更種別 | バグ修正 / 仕様変更 / 仕様追加 / 新規開発 / ドキュメント のいずれか |
| 概要 | 何を変えたかを 1〜3 行で。レビュアーが最初に読む要約 |
| 関連 issue | `Closes #<番号>` / `Fixes #<番号>` |
| 受け入れ基準 | この PR が満たすべき条件をチェックリストで（検証可能な粒度） |
| テスト | 追加・修正したテストと、その観点。手動確認をした場合は手順と結果 |
| ドキュメント | 更新したドキュメント。不要と判断した場合はその理由（`documentation.md` の完了条件）。**`ドキュメント` 種別では「更新範囲」が本欄を兼ねる**ため、本欄は置かない（同じ内容を 2 箇所に書かない） |

## 種別ごとの追加セクション

### バグ修正

| セクション | 書く内容 |
|---|---|
| 事象 | 再現手順 / 期待する挙動 / 実際の挙動。影響範囲（対象ユーザー・データ・期間）も書く |
| 原因 | 根本原因。「どのコードのどの条件で」何が起きたか。表層の症状で止めない |
| 修正方針 | 原因に対してどう手を入れたか。対症療法を選んだ場合はその理由と恒久対応の予定 |
| 再発防止 | 同じ原因を再発させない手立て（回帰テスト・型・ガード・Lint ルール等）。テスト追加が主なら「テスト」と重複させず参照でよい |

### 仕様変更

| セクション | 書く内容 |
|---|---|
| 変更理由 | なぜ既存仕様を変えるのか（要求・課題・意思決定の出どころ） |
| 変更前 / 変更後 | 既存仕様と新仕様を対比で示す（表・箇条書き） |
| 影響範囲 | 影響を受ける機能・API・画面・データ。**後方互換の有無**を明示する |
| 移行手順 | 破壊的変更がある場合の移行方法（データ移行・段階リリース・フラグ・告知）。不要なら「なし（後方互換のため）」 |

### 仕様追加

| セクション | 書く内容 |
|---|---|
| 背景・目的 | なぜこの機能を足すのか。解決する課題 |
| 追加仕様 | 追加した挙動の仕様（入力・出力・条件・エラー時の扱い） |
| 既存への影響 | 既存機能を壊していないことの根拠（触った共通処理・DB スキーマ・権限）。非破壊なら「追加のみ」と根拠を書く |

### 新規開発

| セクション | 書く内容 |
|---|---|
| 背景・目的 | 何のために作るのか。達成したいこと |
| スコープ | **含むもの / 含まないもの**を対で書く。次以降の PR に回した範囲を明示する |
| 設計方針 | 採用した構成・レイヤ分割・主要なライブラリ選定 |
| 設計判断 | 迷った点と選んだ理由（トレードオフ）。レビューで議論してほしい箇所 |
| 残課題 | 既知の未対応・TODO・後続 issue へのリンク |

### ドキュメント

**ドキュメントのみを変更する PR**（仕様書の更新・教訓ログの追記・README 同期・`.claude/rules/` の改訂など）で使う。コード変更を含む場合は使わない（上記「共通ルール」のガードを参照）。

| セクション | 書く内容 |
|---|---|
| 更新理由 | なぜ今更新するのか（コード変更への追随 / 誤りの修正 / 新規記録 / 運用で判明した不足） |
| 更新範囲 | どのドキュメントの何を変えたか。**新規作成 / 追記 / 改訂**のどれかを明示する。全種別必須の「ドキュメント」欄は本欄が兼ねる |
| 正本との関係 | 内容の正本がどこか。**他ドキュメントへ本文を複製していないこと**を確認する（`documentation.md` / `lessons-learned.md` の「本文を複製しない」方針。複製ではなく参照で繋ぐ） |

- **「受け入れ基準」は読み手にとっての条件で書く**（「〇〇を読めば △△ が判断できる」）。ドキュメントにも検証可能な完成条件はある。
- **「テスト」は `なし（ドキュメントのみ）` と書いてよい。** ただし**参照先の見出し・リンク・コード例の実在を確認した場合は、その結果を書く**（参照切れは差分を読むだけでは見つからない）。

## PR テンプレートとの関係

`.github/PULL_REQUEST_TEMPLATE/` に種別別のテンプレートを置く場合も、**必須セクションの正本は本ファイル**とする。テンプレートは本ファイルの見出しを写した骨格であり、両者が食い違った場合は本ファイルに合わせてテンプレートを直す。

## 関連ルールとの分担（重複させない）

| 観点 | 担当ルールファイル |
|---|---|
| PR 本文に何を書くか（本ファイル） | `pr-description.md` |
| issue の起票単位・`Closes #` の運用・サブ issue | `github-issue.md` |
| ブランチ命名・GitHub Flow・push 禁止物 | `git.md` |
| ドキュメント更新の完了条件（影響マップ）・どのドキュメントを更新すべきか | `documentation.md` |
| ドキュメントのみの PR をどう書くか・`ドキュメント` 種別の適用可否 | `pr-description.md`（本ファイル） |
| レビュー前のセルフチェック | `quality-gate.md` |
